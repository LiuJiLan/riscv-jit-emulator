================================================================================
## §1. sigsetjmp / siglongjmp 协议
================================================================================

涉及文件:
  - core/dispatcher.c     (setjmp 调用方)
  - api/helpers.h         (helper 接口声明)
  - jit/translator.c      (emit helper call 时插入寄存器保护)
  - 各 slow path helper   (siglongjmp 调用方,分布在 core / isa / platform)
  - core/trap.c           (架构层 trap 语义,被 helper 在 longjmp 前调用)


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

JIT 块执行中,如果 slow path helper 决定 raise trap(page fault / illegal
instruction / privilege violation 等),需要一种机制把控制权直接交回
dispatcher 主循环,跳过 JIT 块剩余部分。

选择 sigsetjmp/siglongjmp 而不是普通 setjmp/longjmp 的原因:
  helper 在 SIGSEGV handler 触发的路径上可能间接被调用(SMC 失效后重新
  执行的代码会再次走到 helper),需要保证信号 mask 状态正确恢复。


--------------------------------------------------------------------------------
机制
--------------------------------------------------------------------------------

(1) setjmp 端 —— dispatcher
    sigjmp_buf 实体放在 dispatcher 函数自己的栈帧上(局部变量),cpu_t 里
    只持有 sigjmp_buf 指针(jmp_buf_ptr 字段,8 字节)。

    dispatcher 进入主循环前一次性注册 + 一次性调 sigsetjmp;主循环内不再
    调 sigsetjmp:
        sigjmp_buf dispatch_env;
        cpu->jmp_buf_ptr = &dispatch_env;
        sigsetjmp(*cpu->jmp_buf_ptr, 1);   /* 落点同时承接"初次进入"和
                                              "longjmp 跳来"两种路径 */

        while (atomic_load_explicit(&system_reset_signal, memory_order_relaxed) == 0u) {
            /* block 1+2+3, 任何 helper longjmp 都跳回上面那行 sigsetjmp */
        }

    [为什么 sigsetjmp 在 while 外, 不在每轮迭代开头]
      sigsetjmp 的代价 ~50 ns(glibc, 包含信号 mask 操作)。如果放在每轮
      迭代开头,fast path 命中 JIT 块时也付这个代价(每跑完一个块就重新
      建立落点),没意义 —— 落点本身在 longjmp 跳来之前一直有效, 不需要
      "刷新"。一次性建立 + 永久落点是更对的形态。

      副作用: longjmp 跳来后, 栈帧上 dispatcher 的局部变量(total_count
      之类)需要按 dummy.txt §1 末段的规则处理(volatile 或不依赖跨 longjmp
      持久性)。

    [设计理由 —— sigjmp_buf 实体放栈, cpu_t 持指针]
      sigjmp_buf 在 glibc 大约 200 字节,如果直接嵌入 cpu_t 会占用一大块
      cache line。改为指针(8 字节)+ 实体放栈,cpu_t 紧凑,jmp_buf 实体
      生命期天然绑定 dispatcher 线程。

    [未来 hart_host_state_t 拆分]
      jmp_buf 实体已经事实上脱离 cpu_t(在栈),cpu_t 只剩 8 字节指针。
      未来如果做 monitor / shm 暴露(plan §1.14),需要拆出去的主要是其他
      host 侧字段(性能计数器指针、shm 暴露区指针等),不再是 jmp_buf。
      jmp_buf_ptr 字段本身可以继续留 cpu_t,因为它只是一个普通指针,
      不会让"shm 暴露 cpu_t 整体"成为风险。

(2) longjmp 端 —— 两种 raise 路径

    项目里产生 trap 的位置分两类, 它们用不同形态接 trap:

    (2a) interpreter / JIT block 内部 helper —— 经 trap_raise_exception 长跳
       这类 helper(OP_UNSUPPORTED, csr 权限失败, store_helper 越界, ...)
       已经在 block 控制流深处, 退栈到 dispatcher 的清理代价大于直接 longjmp。
       trap_raise_exception 内部:
         a. 调 trap_set_exception_state(hart, cause, tval) 设架构状态
            (检 spec MDT/SDT; 正常 deliver 写 xcause/xtval/xepc + 跳 xtvec + set xDT)
         b. siglongjmp(*hart->jmp_buf_ptr, 1) 跳回 dispatcher 的落点
       trap_raise_exception 标 _Noreturn, 不返回 caller。

    (2b) dispatcher 主帧内 —— 直接调 trap_set_exception_state, 不长跳 (两条子路径)
       已经在 dispatcher 主循环帧内, 控制流回到主循环不需要长跳, 直接调
       trap_set_exception_state(写字段, 不长跳) + return / continue 即可:

       - mmu_translate_pc 取指 fault: 通过返回值告诉 dispatcher "已 deliver,
         continue 这一轮"。dispatcher 看 rc != 0 直接 continue。
       - dispatcher 循环顶 pc IALIGN 兜底 (block 1 之前): 检测 pc 未对齐时
         直接 trap_set_exception_state(CAUSE_INST_ADDR_MISALIGNED, pc) + continue。

       本质规则 (长跳 vs 返回机制的分界) + cause 0 (CAUSE_INST_ADDR_MISALIGNED)
       产生路径细化见 §9。

    两种路径共用同一个 trap_set_exception_state 内核(写字段 + spec MDT/SDT 检查);
    区别只是"控制流如何回到 dispatcher 主循环顶":
    longjmp(路径 a)还是 普通 return + continue(路径 b)。

    (2c) dispatcher 主帧 interrupt 路径 (return-based, 不长跳)
       dispatcher loop 顶每轮调 trap_check_interrupt; 内部按 mip & mie & 全局 IE
       / mideleg 算 ready, 非 0 时调 trap_set_interrupt_state (跟 trap_set_exception_
       state 形态对偶但内部 mideleg/cause_low/tval=0/vectored mode 五点分歧, 详
       trap.c doc). return 非 0 给 dispatcher → continue 跳回 while 顶, 跟
       mmu_translate_pc 失败 (2b) 同形态 return-based 浅栈 dispatcher 主帧, 不长跳.

       跟 (2a) trap_raise_exception 形态不对偶 by design: exception 在 helper 深栈
       必须 longjmp; interrupt 在 dispatcher 主帧浅栈 return + continue 即可. 按
       "对偶不教条" 原则承认形态差异, 内核共用思想 (trap_set_*_state 30 行 mstatus
       翻转完全相同).

    [trap_set_exception_state / trap_set_interrupt_state 的 Double Trap 行为 (spec MDT/SDT)]
      in_trap 嵌套计数字段已废除 (详 trade_off_log §T.9); 改走 spec-defined:
      - S-trap entry 检 sstatus.SDT=1 → unexpected (Ssdbltrp §4.1.1.5): 升级
        deliver_priv=M, cause=DOUBLE_TRAP, mtval2 存原 tval
      - M-trap entry 检 mstatus.MDT=1 → unexpected (Smdbltrp §3.1.6.2): critical-
        error, 不写架构状态, system_reset_signal_set_bit(HART_MDT) 通知 main; 字段
        保留作 root cause 给 main fprintf 看 (项目无 NMI, 走整机 abort)
      - 正常 deliver set 对应 xstatus.xDT=1; mret 清 MDT / sret 清 SDT

(3) 控制流路径

    [前提] dispatcher 入口一次性 sigsetjmp 已建立永久落点, while 条件
    while (system_reset_signal == 0u) 是唯一退出判断 (bitmap, 详 runtime.h)。

    路径 A(无 trap):
      dispatcher 入口 sigsetjmp 一次性建立落点
        → 进 while 循环 (SRS == 0)
        → block 1 (regime / current_tlb)
        → block 2 (mmu_translate_pc 返回 0, 进 block 3)
        → block 3 (interpret_one_block / JIT block 跑完, helper 都正常返回)
        → block 出口
        → 回 while 顶判 SRS == 0, 继续下一轮

    路径 B(interpreter / JIT block 内 helper longjmp, 例如 trap_raise_exception):
      dispatcher 入口 sigsetjmp 一次性建立落点
        → 进 while 循环
        → block 1+2+3 内 helper 调 trap_raise_exception
            → trap_raise_exception 调 trap_set_exception_state(写字段 + spec MDT/SDT 检)
            → siglongjmp(*cpu->jmp_buf_ptr, 1)
        → 回到 dispatcher 入口的 sigsetjmp 落点 (栈帧已退到 dispatcher)
        → 顺序执行到 while 条件, 重新判 SRS == 0
        → SRS == 0 → 继续下一轮 (regs[0] 已是 xtvec, 自然从 trap handler 起点 fetch)
        → SRS != 0 (e.g. M-trap MDT critical-error set HART_MDT) → 退出 dispatcher

    路径 C(dispatcher fetch trap, 不 longjmp):
      dispatcher 入口 sigsetjmp 一次性建立落点
        → 进 while 循环
        → block 2 mmu_translate_pc 内 fetch fault
            → 调 trap_set_exception_state(写字段 + spec MDT/SDT 检)
            → return rc != 0 给 mmu_translate_pc 的 caller(dispatcher)
        → dispatcher 看 rc != 0 → continue (跳过 block 3)
        → 回 while 顶判 SRS == 0, 继续下一轮

    路径 D(dispatcher 主帧 interrupt check, 不 longjmp):
      dispatcher 入口 sigsetjmp 一次性建立落点
        → 进 while 循环
        → 迭代头扫尾 (total_count += local_count)
        → trap_check_interrupt(hart)
            → mip 合成读 & mie & 按 priv 全局 IE / mideleg → ready
            → ready 非 0: 按优先级选 IRQ → 调 trap_set_interrupt_state
                (写 xcause = IRQ | CAUSE_INTERRUPT_BIT, xtval=0, xepc, mstatus
                 xPIE/xIE/xPP 翻转, jump-to base 或 base+4*cause 按 mode)
            → return 非 0 给 dispatcher
        → dispatcher 看 rc != 0 → continue (跳过 DEBUG_REFETCH / IALIGN / block 1-3)
        → 回 while 顶判 SRS == 0, 继续下一轮 (regs[0] 已是 xtvec 入口)

    dispatcher 视角(关键):
      sigsetjmp 返回值不被 dispatcher 用来分流。longjmp 不携带"trap 错误"
      语义 —— 它只是个无条件的"控制流重置到主循环顶部"原语,未来 wfi
      早退 / 中断 fast-forward / 其它"省略中间过程回归 dispatcher"的路径
      也共用这个落点,不需要新机制。
      退出唯一靠 while 条件 (SRS != 0); 派发动作唯一靠状态字段
      (regs[0]/xcause/xtval/xepc/xtvec)。两件事完全解耦。


--------------------------------------------------------------------------------
附:setjmp / longjmp 不快照栈或局部变量
--------------------------------------------------------------------------------

这是 sigsetjmp / siglongjmp 的标准行为,但常被误解为 "longjmp 跳回 = 栈
状态被还原"。事实不是。

jmp_buf 实际记录的内容(寄存器部分,~50 字节):
  - sp (stack pointer) 的值
  - callee-saved 寄存器(RISC-V s0-s11,x86-64 rbx/r12-r15)
  - pc (返回地址)
  - sigsetjmp 还多记一个 sigset_t

glibc 的 jmp_buf 总大小 ~200 字节,差额是 sigset_t + padding,不是栈内容。

longjmp 实际做的:
  把 jmp_buf 里的寄存器值写回当前寄存器,跳到 setjmp 落点。没有任何
  指令碰栈内存。

含义:
  - "sp 还原" 不等于 "栈还原"。sp 是个指针,栈是物理内存。
  - sp 之上(setjmp 那一帧自身的地盘)的栈变量如果在 setjmp / longjmp
    之间被修改(例如 helper 拿到地址写),longjmp 后这些修改保留 ——
    没有任何机制去擦它们。
  - sp 之下(被遗弃的栈帧)的内容物理上还在,但软件约定上不再可达;
    后续函数调用会覆盖写。
  - callee-saved 寄存器被还原 → 编译器若把变量放进 callee-saved 寄存
    器,变量"看起来被快照";若放栈,变量不被快照。
  - 编译器选哪个不可预测,因此 C 标准把 "setjmp 之后被修改的非
    volatile 局部变量" 定义为未定义行为(UB)。

实践:
  - 任何跨 setjmp / longjmp 反复读写的 dispatcher 局部变量(典型如
    local_counter)必须声明为 volatile,否则 UB。
  - volatile 不等于"还原到 setjmp 时的值",而是"行为变成确定的:取
    helper 最后一次写入的值"。
  - 若某场景真的需要"还原一组变量到 setjmp 时的快照",标准做法是:
    (a) 把这些变量声明为 volatile
    (b) 在 setjmp 后显式调 restore_state(),从某个不变区拷回
    setjmp 本身不提供这个能力。


--------------------------------------------------------------------------------
Translator 配合机制(寄存器保护)
--------------------------------------------------------------------------------

JIT 块内会把部分 guest 寄存器映射到 host 寄存器以加速 fast path。
helper 用 longjmp 跳走时,host 寄存器的值会丢失,但 trap 处理依赖 cpu_t
里的完整 guest 寄存器状态。

策略 —— 统一保护(初版决定):
  Translator 在 emit 每个 helper call 前,插入一段 store 指令把所有当前
  映射在 host 寄存器的 guest 寄存器写回 cpu_t;helper call 后再 restore
  回来。

  好处:简单、无 bug 风险、不需要 helper 元信息系统。
  代价:
    - fence.i / wfi 等本来不会 longjmp 的 helper 也付保护代价
      → 但这些是低频 helper,代价不显著
    - store_helper 是高频 + may-longjmp,每次 store 都付保护代价
      → 但 store 本身在 helper 里要做的事多,几条额外 mov 占比不显著


--------------------------------------------------------------------------------
为什么没选"按 helper 标注 may-longjmp / pure"
--------------------------------------------------------------------------------

考虑过给每个 helper 标注 may_trap / pure 属性,translator 据此决定加不加
store/restore。否决理由:

  1. 高频路径上的"pure helper"很少
     真正可能漏标的高频 helper(store_helper、load_helper、csr_xxx、
     amo_helper)几乎都是 may-longjmp。
     pure 的(fence.i、wfi、纯计算 helper)本来就是低频。

  2. 漏标 bug 极隐蔽
     如果某个其实会 longjmp 的 helper 被标为 pure,寄存器值在 trap 后变
     脏,handler 重新进 dispatcher 时拿到错的 cpu_t 状态。难追。

  3. 收益小、复杂度大
     省下的 store/restore 在 helper 总开销里占比小;但维护标注系统的
     心智负担和 bug 风险长期存在。

  → 统一保护(策略选择)


--------------------------------------------------------------------------------
未来改进点
--------------------------------------------------------------------------------

(F1) store_helper inline 化(命名澄清:不是"store 变 fast path")
     **重要术语澄清**:历史命名"store fast path inline 化"有误导性。
     store_helper 内部所有操作(misalign 检查 / TLB lookup / walker
     fall back / reservation 清除 / SMC 检测)都是 slow path 性质的
     操作,改进后这些操作仍全部是 slow path。inline 化只是改 store_helper
     的链接形态(extern 函数 → static inline 函数 / 或 JIT emit-equiv),
     消除每次 store 付的函数 call/ret 开销(5-15 cycle)+ 寄存器保护代价。

     初版所有 store 都走 store_helper(extern 函数 call),因此每次 store
     都付:(a) call/ret 开销;(b) 寄存器保护代价(dummy.txt §1 "统一保护")。
     未来 store_helper inline 化后:
       - 函数 call 开销消失(代码内联进调用方 case)
       - 寄存器保护代价集中在 helper 内真正 may-longjmp 的子段
         (reservation 清除 / 真正 fall back walker 的路径)上
     这等于自动消化了"统一保护"在 store 路径上的成本,但 store_helper 仍是
     slow path —— 只是这条 slow path 的边界从"函数边界"挪到"代码块边界"。
     完整设计留作未来改进 (对齐时一并修正历史命名误导)。

(F2) 性能 profile 后,如果某个低频 pure helper 意外成为热点,可以单独
     为它加 "no_save" 标注。这是局部优化,不破坏架构。


--------------------------------------------------------------------------------
附: load / store 不对称的真机理
--------------------------------------------------------------------------------

虽然本协议主体讲 sigsetjmp/siglongjmp, 但 load/store 路径上有一个相关
的不对称, 直接影响"哪些 helper 真的会 longjmp"。

不对称的因果链 (5 条):

  1. TLB 缓存的是 hva (tlb_e_t.host_ptr, 见 tlb.h), 不是 pa
  2. MMIO 不进 TLB (§4 单分发表 + §8 三层模型)
  3. → TLB 命中路径**结构上**不带 RAM/MMIO 分支 — entry 内根本不可能是
     MMIO, 命中路径不需要 IS_GPA_RAM check
  4. → load 命中可以**直接 return *hva**, 不需要任何子 helper
  5. store 命中仍然必须走 store_helper — 不是因为"store 慢点也无所谓",
     而是 LR/SC reservation 清除 / 未来 SMC 副作用强制经 helper, 跟
     RAM/MMIO 分流无关

也就是: load / store 不对称 = "副作用强制经 helper vs 没副作用可走 TLB
直接 *hva", **不是** "性能 vs 副作用" 二分。

"MMIO 不进 TLB" 的真意 = "让 TLB 命中路径结构上不带分支", 不是单纯"省
TLB 空间 / MMIO 命中率低"。

完整调用拓扑 + 接口签名见 src/isa/lsu.h 顶段; mmu 端见 src/core/mmu.h 顶段。

为什么 store 不能简单 inline:
  - LR/SC 语义: 任何 store 都可能让某 reservation 失效; reservation 检查
    放在 store_helper 内部
  - 未来 SMC 检测: 可能让 store 路径配合 page_dirty 位图 (替代 SIGSEGV)
  - 接口稳定: reservation 暂未真做, 接口仍保 store_helper 形态, 未来加
    副作用只改 helper 内部, 不改调用方

性能影响 (统一保护策略下):
  - 解释器: 每个 store case 走 helper (~10-20 cycle), 占比小
  - JIT: 每个 store emit 一个 helper call, 每次付寄存器 store/restore
    (这正是本节 "统一保护" 所付的代价)

→ 这个不对称在 §4 (TLB) / §8 (三层模型) 各自有体现, 此处把它和 longjmp
  协议的关系说清楚。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不处理"helper 内部主动取消 trap 决定"的情况(没有这种场景:
    helper 一旦决定 raise,就直接 longjmp,没有"想了想算了")。

  - 本协议不处理 SIGSEGV handler 自身的 longjmp(handler 本身只写
    page_dirty bitmap,不参与 trap 处理流程,见 jit/smc.c 的 SIGSEGV
    handler 设计)。


================================================================================
## §2. x0 寄存器的全局编码约定
================================================================================

涉及文件:
  - core/cpu.c            (cpu_t 字段布局,x0 不存)
  - jit/translator.c      (emit 时对 x0 的读写特判)
  - jit/ir.h              (IR 对寄存器的统一抽象,不感知 x0 特殊性)
  - jit/backend.h         (后端不感知 x0 特殊性)
  - core/interpreter.c    (解释器路径同样需要遵守)


--------------------------------------------------------------------------------
背景
--------------------------------------------------------------------------------

RISC-V x0 寄存器恒为 0:
  - 读 x0 → 永远得到 0
  - 写 x0 → 合法(NOP 语义),但写入值被丢弃

cpu_t 内存布局选择"pc 在偏移 0,x1..x31 在偏移 4..124"(见 §A.cpu),
即 cpu_t **不为 x0 保留物理位置**。这意味着:
  - 偏移 0 处实际是 pc,不是 x0
  - 任何走"reg_idx * 4"算偏移的代码,如果不特判 x0,会把 pc 当 x0 用


--------------------------------------------------------------------------------
约定
--------------------------------------------------------------------------------

(1) 读 x0
    Translator 在 emit "读寄存器 r"的代码时:
      if (r == 0) emit 立即数 0
      else        emit "load from cpu_t + r*4"

    解释器执行 "读寄存器 r":
      if (r == 0) 直接用 0
      else        cpu->regs[r-1]   (或等效的偏移访问)

(2) 写 x0
    Translator 在 emit "写寄存器 r = expr"的代码时:
      if (r == 0) emit "store expr to <局部垃圾桶变量>"
                  (或等效:emit 一个 dead store,寄存器分配器消除)
      else        emit "store expr to cpu_t + r*4"

    解释器执行 "写寄存器 r":
      if (r == 0) 不做任何事(简单丢弃)
      else        cpu->regs[r-1] = expr


--------------------------------------------------------------------------------
为什么用"局部垃圾桶变量"而不是"emit 时直接跳过 store"
--------------------------------------------------------------------------------

看似 "if (r == 0) skip emit" 更简单,但实际有问题:

  - 写 x0 的指令的右操作数 expr 可能有副作用(例如 `addi x0, x1, imm`
    虽然结果丢弃,但表达式本身的求值不影响什么;但如果是更复杂的指令
    或后续优化引入了副作用 helper,跳过 store 会让 IR 不一致)
  - 更重要:统一性。让 IR / backend 不必感知 x0 的特殊性,对所有寄存器
    走同一条"emit store"路径,翻译规则简单 + 后端无需特判
  - 局部垃圾桶变量在寄存器分配阶段是 dead store,任何过得去的后端都会
    在死代码消除时干掉,不影响最终代码质量


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本约定不限制 cpu_t 内存布局的其他自由度(字段顺序、对齐等),只规
    定"x0 不在 cpu_t 里有物理位置"
  - 本约定不影响 reservation / CSR / FP 寄存器的处理,只覆盖通用整数
    寄存器 x0..x31

## §3. satp 字段合法性契约
================================================================================

涉及文件:
  - core/csr.c            (satp 读写 helper —— 契约的"生产者")
  - core/dispatcher.c     (按 satp.ASID 索引叶 TLB —— 契约的"消费者")
  - 涉及 tlb 数据结构本身(无函数接口,但 dispatcher 的索引行为依赖此契约)


--------------------------------------------------------------------------------
契约
--------------------------------------------------------------------------------

**csr.c 必须保证:任何时候 cpu_t->satp 字段中的 ASID 位都是合法的。**

具体含义:
  - "合法"指 ASID 值在 [0, ASID_MAX) 范围内
  - ASID_MAX = 1 << TLB_ASID_BITS(本项目配置:1 << 4 = 16)
  - 所有写入 cpu_t->satp 的代码路径(初始化、CSR 写 helper、可能的 trap
    handler 内部修改等)都必须执行 WARL 截断:
      cpu->satp = (value & ~ASID_MASK) | (extract_asid(value) & (ASID_MAX - 1));
  - RV 规范允许实现少于 ASIDMAX(Sv32 ASIDMAX=9)的 ASID 位数,WARL 行为
    本来就是规范要求的


--------------------------------------------------------------------------------
依赖
--------------------------------------------------------------------------------

**dispatcher.c 信任此契约,直接按 satp.ASID 索引叶 TLB 数组,无范围检查:**

  asid_t asid = extract_asid(cpu->satp);
  tlb_t *leaf_tlb = sv_asid_array[asid];   // 直接索引,无 bounds check

  if (leaf_tlb == NULL) {
      // 懒分配:此 ASID 第一次被使用
      leaf_tlb = aligned_alloc(64, sizeof(tlb_t));
      sv_asid_array[asid] = leaf_tlb;
  }


--------------------------------------------------------------------------------
为什么必须是契约,不是运行时检查
--------------------------------------------------------------------------------

(1) **fast path 性能**:dispatcher 进入每个块前都要选 TLB 指针。如果每次
    都做 bounds check,等于在 dispatcher 路径上加一条额外的 cmp + branch,
    且这个 branch 100% 命中"合法",纯浪费。

(2) **责任集中**:满足契约的代码集中在 csr.c 的几个 satp 写入路径(可能
    只有 1-2 处)。一次写好 + 单元测试覆盖 + 这条契约文档,比让每个消费者
    各自检查可靠得多。

(3) **host 内存安全**:违反契约 → dispatcher 越界访问 asid_array →
    段错误或读到野指针。这是 host 内存安全问题,不是 guest 行为正确性
    问题,必须从源头杜绝。


--------------------------------------------------------------------------------
违反后果
--------------------------------------------------------------------------------

如果某天 csr.c 的某条 satp 写路径漏了 WARL 截断:
  - 调试现象:dispatcher 在某些 satp 值下段错误,但 guest 行为看起来"正常"
  - 排查方向:**先怀疑 csr.c 的 satp 写路径**(本契约的"生产者"职责),
    不是 dispatcher 的问题
  - 单元测试建议:csr.c 的 satp 写 helper 单测必须覆盖
    "写入超出 ASIDLEN 的 ASID 值,验证读回的值已被截断"


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本契约不约束 satp 的其他字段(MODE / PPN);它们的 WARL / 合法性
    由 csr.c 自行管理,不影响 dispatcher 的索引行为
  - 本契约不延伸到其他 CSR(mstatus、mip 等);它们没有"被 dispatcher
    用作数组索引"这种危险操作,所以 WARL 失败最多导致 guest 行为不对,
    不会导致 host 段错误

## §4. TLB 作为 block 入口的统一分发机制
================================================================================

涉及文件:
  - core/dispatcher.c     (block 派发的执行者,fetch 路径过 TLB)
  - core/interpreter.c    (block 内代码消费 TLB 拿到的 host pointer)
  - jit/translator.c      (JIT 翻译 emit 的代码也基于 TLB)
  - core/tlb.{c,h}        (TLB 数据结构 + 装载机制)
  - core/mmu.c            (TLB miss 时由 walker 填表;M/bare 下 walker short-circuit)


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

TLB 在本项目里不只是 GVA → HA 的缓存,还充当 "以入口 pc 为 key 的 block
分发表"。dispatcher / 解释器 / JIT 翻译器都通过 TLB 拿 host pointer 来
执行 block,而不是各自直接计算地址。

这条设计直接决定了 block 入口的唯一性、跨 priv 复用性、以及 M/bare
模式下 "看似可以绕过 TLB" 为什么也不绕。


--------------------------------------------------------------------------------
block 入口的唯一性
--------------------------------------------------------------------------------

任何一个 block(无论由 JIT 还是解释器执行),其入口 pc 在派发表中只有
一份生效条目:

  - JIT 路径:jit_cache 以 PA 为 key(plan §1.4),同一 PA 入口只有一个
    cache 条目,不会有两份并存的 "同入口翻译"
  - 解释器路径:执行流上一次只走一个 block,入口仍由 dispatcher 拿当前
    pc 来确定

block 内的子段(JIT 翻译过程中的局部块,例如某 else 分支长期 trap 导致
后续段被截断重新编译)允许重复存在 —— 但这些是子段,不是 "入口"。
入口仍然唯一。


--------------------------------------------------------------------------------
bare 模式下也走 TLB(关键设计)
--------------------------------------------------------------------------------

M 态 / S 态的 bare 模式下,gva == pa(恒等映射)。一种朴素实现可能想
"这种情况直接拿 pc 算 host pointer,跳过 TLB"。本项目不这样做。

理由:dispatcher 是按 "入口 pc → 块" 做派发的,要做到统一派发就需要
一个统一的分发表;TLB 就是这个分发表。如果 bare 模式绕开 TLB,bare
路径和有页表路径就分裂成两条派发流程,代码量、JIT 翻译产物、调试路径
都翻倍。

具体:

  - M/bare 模式下,TLB 仍被装载,装载的内容是恒等映射条目
    (gva → host_ram_base + (gva - GUEST_RAM_START))
  - mmu walker 在 M/bare 下是 short-circuit(直接返回 gva = pa,不走真
    页表),但 TLB miss 路径仍然调 walker 填表
  - 解释器和 JIT 翻译产物都通过 TLB 拿 host pointer,不论 priv 模式


--------------------------------------------------------------------------------
收益
--------------------------------------------------------------------------------

  (1) dispatcher 派发逻辑不感知 priv 模式
      不论 M/bare/S+页表,dispatcher 干的事都是 "拿 leaf TLB 指针 →
      fetch 入口 → 调 block"。priv 切换时只切 leaf TLB 指针,派发主
      循环不动。

  (2) JIT 翻译产物跨 priv 复用
      JIT 翻译出的 host code 通过 TLB 拿 host pointer。同一 PA 在 M
      态和 S 态产生的翻译产物可以共用(jit_cache key 是 PA),无需
      为不同 priv 编两份。

  (3) 单一调试路径
      "block 跑不动了" 无论 priv 模式,都查同一个分发表 + 同一组 walker
      逻辑,不必为不同模式准备不同诊断手段。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本机制不规定 block 入口处 host pointer 的具体派生方式(TLB 命中
    vs miss 后填,各自的代码形态由 §2.tlb / §3.mmu 决定)
  - 本机制不覆盖 block 内 load/store 的 TLB 路径,但相关协议见
    本文 §1(sigsetjmp / 寄存器保护)和 dummy.txt 整体的 fast/slow
    path 哲学
  - 本机制不规定 TLB 实现的具体阶段时序(各 milestone 实现到哪一步由
    file 自身决定; 本协议描述的是稳定状态)

## §5. 报错风格协议
================================================================================

涉及文件:
  - src/main.c            (调用方:模块入口的调用者)
  - 各模块入口函数        (loader / ram / cpu / mmu / csr / interpreter ... 的对外入口)
  - 各模块内部 helper     (实际接触 errno / 失败副作用的最深帧)


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

模块出错时,stderr 上的输出既不能重复说同一件事,也不能漏说细节。约定
一套分工,让每条失败恰好产生两行(内部 why + 外部 where),内容互补不
重叠。

模块入口对外永远只回 0/-1(工厂语义下回指针/NULL),不引入 enum 错误码。
具体为什么失败,由实际接触失败副作用的那一帧 fprintf 自己说。


--------------------------------------------------------------------------------
分工规则
--------------------------------------------------------------------------------

(1) "why" 行:由实际接触 errno / 失败副作用的那一帧 fprintf
    内容:模块名 + 失败步骤 + errno(strerror)+ 相关参数(path / size / ...)
    示例:
      fprintf(stderr, "ram_init: mmap failed: %s\n", strerror(errno));
      fprintf(stderr, "loader_load_bin: open(%s) failed: %s\n", path, strerror(errno));
      fprintf(stderr, "loader_load_elf: not implemented\n");

(2) 该帧之上(包括模块入口、main),不再二次 fprintf "why",只 propagate
    错误码(return -1 或 return NULL)。

(3) "where" 行:由模块入口的调用方(通常是 main)fprintf
    内容:只说哪个模块入口失败,不带 err 值。
    示例:
      fprintf(stderr, "ram_init failed\n");
      fprintf(stderr, "load failed\n");

(4) 模块内部若再细分 helper(例如 loader_load_bin 内部 helper
    read_into_buffer):helper 是"实际接触失败副作用的最深帧",由
    helper 报 why。loader_load_bin 不再报 why,只 return 错误码向上传。

(5) 任何失败,stderr 上恰好两行:1 行内部 why(最深帧)+ 1 行外部 where
    (调用方)。


--------------------------------------------------------------------------------
为什么不引入 enum 错误码
--------------------------------------------------------------------------------

  - 模块入口对外只表达"对/错"。enum 是给调用方按失败种类做差别处理用
    的。本项目调用方(main / 上层模块)对失败种类没有差别处理:全部
    当作"模块挂了",报 where 然后 return / 退出。
  - 没有差别处理却维护 enum,等于多一份枚举集要维护、多处 -Wswitch-enum
    潜在警告点,无收益。
  - 真有差别处理需求时再加 enum 不晚(C 里 enum 是廉价的)。


--------------------------------------------------------------------------------
为什么不维护 *_strerror 翻译表
--------------------------------------------------------------------------------

  - 翻译表是 enum 路线的配套,前提是模块入口对外暴露错误种类。本协议
    根本不暴露错误种类,翻译表无对象可翻译。
  - "具体什么挂了"已经由内部 fprintf 直接说,翻译表没有信息增量。


--------------------------------------------------------------------------------
模块不调 exit
--------------------------------------------------------------------------------

  模块入口失败时只 return 错误码 / NULL,不调 exit。模块边界保住,便于
  未来嵌入测试 harness 或长期运行进程时复用。
  调 exit 由 main(或顶层 driver)决定。


--------------------------------------------------------------------------------
运行中内部一致性违例 — runtime_fatal (跟启动期失败码两条路)
--------------------------------------------------------------------------------

  上面整套 (return 码 + why/where 两行) 针对的是 *启动期* 失败 (lifecycle 早期、
  单线程、调用方能决定退不退)。**运行中** 检测到 emulator 内部一致性违例 (不该
  发生的状态 = 真 host 侧 bug, 例: PLIC 反查表 plic_ctx_to_hartid / plic_ctx_map
  读到 -1, 见 §15 第 3 类越界) 是另一条路: 此时多线程已起、调用栈可能持锁, 返码
  上抛没意义 (没人能"决定不退"), 必须主动停全机 + 留 dump 定位。

  走 runtime_fatal(where, detail, bad_value) (runtime.{c,h}; where 传 __func__):
    - fprintf 一行诊断 (where = 出事函数名, bad_value = 读到的非法值);
    - 紧急全机停机: SDS + SRS 各 set INTERNAL_FATAL bit (走顺序 B = SDS 先 SRS 后,
      详 runtime.h 顶段 "顺序 B 防 race" 段);
    - wfi_kick_all 叫醒所有可能在 WFI 的 hart (让它们 re-check predicate 看 SRS 退);
    - main while 退出 → 正常 cleanup chain + cpu_dump (定位现场)。

  约束 (跟 "模块不调 exit" 同源精神, 但更强):
    - **non-_Noreturn / 不 abort()**: call site 可能持锁 (plic recompute 持
      plic.lock wrlock), C abort()/longjmp 会带锁跳走死锁; 必须正常返回让栈
      unwind 出锁, call site 调用后自行安全 return (防 -1 二次越界索引)。
      真正的 abort() (core dump) 不引入 — 协同停机保住 main 的 cleanup 控制权,
      跟本协议 "调 exit 由 main 决定" 初衷一致。
    - runtime_fatal 是唯一可由 SRS 类 (dispatcher/hart/trap) 和 SDS 类 (timer/
      uart/virtio) 设备都直接调的跨类停机包装 (有意的跨类例外, 详 runtime.h)。


--------------------------------------------------------------------------------
stderr vs stdout
--------------------------------------------------------------------------------

  错误信息一律走 stderr。stdout 留给将来正常输出(guest console、监控
  数据等)。混用会让正常输出脏。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不规定信息的人类可读语言(中英文皆可,但同一模块内一致)。
  - 本协议不覆盖"helper 通过 longjmp 跳走"的路径(那是 §1 的范畴,
    不走这套 fprintf)。
  - 本协议不规定日志级别 / 日志文件 / syslog;项目当前全部走 stderr 即可。

## §6. CSR 物理存储字段命名五类划分
================================================================================

涉及文件:
  - src/core/trap.h          (trap_csrs_t 字段; _mstatus / _medeleg / xtvec[4] 等)
  - src/core/cpu.h           (cpu_t 内嵌 trap_csrs_t; cpu_info_per_hart_t / cpu_info_shared_t)
  - src/core/csr.c           (csr 入口 read/write helper 按命名前缀直读字段)
  - 未来 isa/fpu.h           (F/D 扩展; _fcsr 类 1 拆 fcsr/fflags/frm 三入口)
  - 未来 isa/vector.h        (V 扩展; vstart/vtype/vl 等)


--------------------------------------------------------------------------------
背景
--------------------------------------------------------------------------------

CSR 在 RV spec 里数量很多 (M-mode 几十个, S-mode 几十个, F/V/Debug 扩展更多)。
项目把这些 CSR 物理存储分散在不同 struct(trap_csrs_t / cpu_info_per_hart_t /
cpu_info_shared_t / 未来 fcsr_t 等), csr.c 大 switch 的 read/write helper 按命名
直读字段。命名规则统一才能在不同 struct 间一致, 让"读到字段名就知道访问形态"。


--------------------------------------------------------------------------------
五类划分
--------------------------------------------------------------------------------

(1) 第一类 — RV32 物理 64 位, csr 入口拆 32 位访问
    命名前缀: 下划线 "_"
    类型: uint64_t
    示例:
      _mstatus  — 物理一份 uint64_t 字段; 三个 csr 入口同级看这一份字段:
                    mstatus  (0x300) — 低 32 位
                    mstatush (0x310) — 高 32 位
                    sstatus  (0x100) — 低 32 位 ∩ SSTATUS_MASK
                  三个入口都是 _mstatus 字段的访问通道, sstatus 不是"mstatus 的派生",
                  跟 mstatus / mstatush 同级 (实现上 csr.c 三个 read/write helper 各自
                  对 _mstatus 字段做 mask/shift, 互相不调)。
      _medeleg  — priv spec 1.12 定义 medelegh (0x312) 为 RV32 高 32 位入口, 物理 64
                  位存 cause bitmap (RV64 单入口整体访问)。项目当前只实装 medeleg 低
                  32 位入口 (medelegh 未实装), 字段类型 uint64_t 已 RV64-ready。
                  注: mideleg (M-mode 中断 delegation) 是 MXLEN-bit (RV32 = 32 位, spec
                  未定义 midelegh), 属类 3 不带前缀, 不属本类。

    csr.c read/write helper 模式:
      static uint32_t csr_mstatus_read (cpu_t *hart) {
          return (uint32_t)(hart->trap._mstatus & 0xFFFFFFFFu);
      }
      static uint32_t csr_mstatush_read(cpu_t *hart) {
          return (uint32_t)((hart->trap._mstatus >> 32) & 0xFFFFFFFFu);
      }

    [为什么单独提取出 (1) 类]
    (1) 类的本质特征 (内部字段长度 ≠ 外部 csr 入口长度) 跟 RV 寄存器长度 (xlen=32 / 64)
    解耦 — 同一个 _mstatus 字段在 RV32 下是 mstatus + mstatush 两入口拆访问 (各 32 位匹
    配 xlen=32), 切到 RV64 下是 mstatus 单入口整体访问 (64 位匹配 xlen=64), 字段类型
    uint64_t 全程不变。

    提取 (1) 类做 future-proof: RV32 → RV64 切换时只需改 csr 入口形态 (拆访问 → 整体访问,
    csr.c read/write helper 重写), 不需要改字段类型 + 不需要重新 layout cpu_t / trap_csrs_t。
    这也是为什么 _mstatus / _medeleg 当前都用 uint64_t 而不是 uint32_t — 哪怕项目当前
    RV32 实际只用低 32 位, 物理类型已经 RV64-ready。

(2) 第二类 — 副本类 (一个物理字段被多个 csr 入口看, 入口之间不存在派生关系, 各看不同 mask)
    命名前缀: 下划线 "_" (跟第一类同前缀, 因都是物理跨多入口/多视图字段)
    分两种子情况:
      (2a) 权级副本 — 同一份物理字段, 多个 csr 入口同级看不同 mask 子集
           示例 1: _mstatus 字段被 mstatus / sstatus 两个 csr 入口看 (mstatush 跟 sstatus
                   不算副本关系, 是低/高半边关系, 见 (1)+(2a) 特殊段); mstatus 入口看低 32
                   位全部, sstatus 入口看低 32 位 ∩ SSTATUS_MASK = SIE|SPIE|SPP|SUM|MXR;
                   两入口实现独立 (csr.c 三个 helper 不互调), 关系是"同级看不同 mask",
                   不是"sstatus 派生于 mstatus"。
           示例 2: _mie 字段 (uint32_t) 被 mie / sie 两个 csr 入口看; mie 入口看全部 32 位
                   (项目用 bit 1/3/5/7/9/11 = IRQ_S/M × SOFT/TIMER/EXT 六位), sie 入口看
                   32 位 ∩ SIE_MASK = IRQ_S × SOFT/TIMER/EXT 三位 (bit 1/5/9)。两入口实现
                   独立 (csr.c 两个 helper 不互调), 关系是"同级看不同 mask"。
                   _mie 跟 _mstatus 的区别: _mstatus 是 (1)+(2a) 特殊 (物理 64 位, csr 入口
                   拆访问 + masked view 两个性质叠加); _mie 是单纯 (2a) (物理字段长度 ==
                   csr 入口长度, 只有 masked view 一个性质)。"_" 前缀依据是 (2a) "物理跨
                   多入口/多视图", 不是 (1) "长度差"。
                   (注: mip / sip 入口对应的物理字段是 _mip_sw, 不属类 (2a) — 因 mip
                   readout 不只是某物理字段的 mask view, 还要 OR 异步源 (CLINT.msip /
                   PLIC) + compute (mtime≥mtimecmp). 见 (5) 类。)
      (2b) csr / MMIO 副本 — 一个物理字段同时被 csr 入口和 MMIO load/store 读写
           示例: _mtime (CLINT MMIO 0xBFF8 同时被 csrr time 读 + MMIO load 读, 两路径同源字段)

    项目当前 (2a) 真字段 = _mstatus (mstatus + sstatus 两入口看) / _mie (mie + sie);
    (2b) 没遇到真字段 (clint / plic 真做时加)。mip / sip 入口的物理字段 _mip_sw 属类
    (5) 软件可写子集 + 异步源合成读, 不属本类 — csr readout 是合成结果而不是字段的
    mask view。

(*) (1) + (2a) 特殊例子: _mstatus / _fcsr / _vcsr — 同时满足"物理一份长字段, 多 csr 入口
    同级看不同 sub-view"
    类 (1) 的本质是"物理字段长度 ≠ 任一 csr 入口长度", 模拟器内一份大字段, 多 csr 入口各自
    通过 mask / shift 看子段; 类 (2a) 是"同一份字段被多 csr 入口同级看不同 mask 子集" — 两者
    在 sub-view 关系里其实重叠 (一份字段, 多入口同级看不同 view)。下列字段同时属 (1) + (2a),
    命名统一取 "_" 前缀:
      _mstatus  — 物理 64 位; 三个 csr 入口同级看: mstatus(0x300, 低 32) +
                  mstatush(0x310, 高 32) [类 (1) 拆 xlen 访问] + sstatus(0x100, 低 32
                  ∩ SSTATUS_MASK) [类 (2a) mask 子集; SSTATUS_MASK = SIE|SPIE|SPP|SUM|MXR]。
      _fcsr     — RV spec 规定 fcsr 32 位 (项目当前未实装 F 扩展; 真做时按本协议加)。
                  三 csr 入口同级看: fcsr(32 位全部) + fflags(5 bit, fcsr[4:0]) +
                  frm(3 bit, fcsr[7:5]); fflags/frm 是 _fcsr 字段的 mask 子集 (2a) — 跟
                  fcsr 入口同级, 不是 fcsr 入口的派生。
      _vcsr     — RV spec 规定 vcsr 是 vxsat + vxrm 的组合视图; 三 csr 入口同级看:
                  vcsr / vxsat(bit 0) / vxrm(bit 2:1) (跟 _fcsr 同形态)。

(3) 第三类 — priv 无关独立寄存器 (单字段, 单 csr 入口, 无 sub-view / 无副本)
    命名前缀: 不带前缀 (普通字段名)
    示例:
      mideleg — M-mode 中断 delegation bitmask, MXLEN-bit (RV32 = 32 位; spec 未定义
                midelegh, 中断 cause 不会超 32 位)。单字段单 csr 入口 (0x303), 字段类型
                uint32_t, csr.c read/write helper 直读 (无 mask/shift)。
                trap_set_interrupt_state 按 mideleg.bit(cause_low) 派发 deliver_priv,
                trap_check_interrupt 用 mideleg 算 deliver_mask。
      (未来) RV Unprivileged Vector CSRs 中的独立部分:
          vstart  — 单字段 (vector start position)
          vtype   — 单字段 (vector type, RW with WARL)
          vl      — 单字段 (vector length, RO from M-mode 写视角; vsetvl 指令写)
        各自单 csr 入口, 单字段, 没 sub-view; 跟 vcsr 系列 (上面 (*) 特殊) 区分。

(4) 第四类 — 按 priv 索引数组
    命名前缀: "x" 前缀 (跟 RV 手册风格一致, 手册用 xepc 同时指代 mepc/sepc)
    数组下标 = deliver priv (PRIV_M=3 / PRIV_S=1 / PRIV_U=0 占位 / PRIV_H=2 占位)
    示例:
      xcause[4]   — mcause (xcause[PRIV_M]) / scause (xcause[PRIV_S])
      xtval[4]    — mtval / stval
      xepc[4]     — mepc / sepc
      xtvec[4]    — mtvec / stvec
      xscratch[4] — mscratch / sscratch

    csr.c read/write helper 模式:
      static uint32_t csr_mepc_read(cpu_t *hart) { return hart->trap.xepc[PRIV_M]; }
      static uint32_t csr_sepc_read(cpu_t *hart) { return hart->trap.xepc[PRIV_S]; }

(5) 第五类 — 软件可写子集 + 异步源 OR 合成读
    命名前缀: 下划线 "_" + 后缀 "_sw" 或 "_hw" (后缀表 "字段不是完整 csr source,
    是入口可写位的物理子集"; 跟类 (2a) 区分 — (2a) 字段是完整 csr source 被多入口
    看 mask 子集)
    特征:
      - 物理字段只存 "csr 入口的软件可写位 (后缀 _sw) 或硬件 set 位 (后缀 _hw)",
        位号 layout 跟 csr readout view 一致 (bit 编号 = RV spec 寄存器位号)
      - 读时不直接返回字段; 字段 OR 异步源 / compute 派生 = 完整 csr readout
      - 写时只动字段对应的部分 (_sw 字段被 csrw 写; _hw 字段不被 csrw 影响, 由
        硬件源驱动)
      - 跟 (2a) 区别: (2a) 无 "OR 异步源" 层, 多入口只是 mask view; (5) 物理字段
        **不是完整 csr source**, 而是 csr 入口的子集; csr readout 要靠合成
      - 跟 (2b) 区别: (2b) 同源字段被 csr + MMIO 两路径访问 (物理字段是完整 source);
        (5) csr 入口的部分位由 "异步源 / compute" 提供, 字段只存 csr 入口的另一部分位
    示例:
      _mip_sw  — mip 入口软件可写子集 (uint32_t, bit 1 SSIP / bit 5 STIP / bit 9
                  SEIP_sw, 其他位永远 0)。csrr mip 时 OR 以下源得完整 mip readout:
                    bit 3  ← CLINT.msip[hartid] (异步源, atomic load; MSIP RO in mip)
                    bit 7  ← (mtime ≥ mtimecmp[hartid]) (compute; MTIP RO in mip)
                    bit 9  ← _mip_sw 该位 OR PLIC s_pending (未来; v1 永远 0)
                    bit 11 ← PLIC m_pending (未来; v1 永远 0)
                  csrw mip 只动 _mip_sw 对应位 (MIP_SW_WRITABLE_MASK = bit 1|5|9);
                  其他位 (MSIP/MTIP/MEIP) 写忽略。
                  sip 入口 = mip 入口 ∩ SIP_MASK 之后再合成 (mask view 套在合成
                  之上); csrw sip 只动 _mip_sw bit 1 (SSIP RW; STIP / SEIP RO in sip
                  按 RV spec §5.1.4 强制).

    项目当前 (5) 真字段 = _mip_sw 唯一 (sw 子集形态); 未来 SEIP 真两 bit 视图实
    装时加 _mip_seip_hw (hw 子集形态; 当前 hw_seip 路径占位返 0); H/AIA 扩展可
    能再加.

    csr.c read/write helper 模式:
      static uint32_t csr_mip_read(cpu_t *hart) {
          uint32_t mip_view = hart->trap._mip_sw;
          uint32_t hartid = hart->per_hart_info.mhartid;
          if (atomic_load_explicit(&clint.msip[hartid], memory_order_acquire))
              mip_view |= (1u << IRQ_M_SOFT);
          if (atomic_load_explicit(&clint.mtime, memory_order_acquire) >=
              atomic_load_explicit(&clint.mtimecmp[hartid], memory_order_acquire))
              mip_view |= (1u << IRQ_M_TIMER);
          /* (未来) mip_view |= plic_m_pending(hartid) ? (1u << IRQ_M_EXT) : 0; */
          /* (未来) mip_view |= plic_s_pending(hartid) ? (1u << IRQ_S_EXT) : 0; */
          return mip_view;
      }
      static void csr_mip_write(cpu_t *hart, uint32_t v) {
          /* 只动 _mip_sw 对应位 (M-mode csrw mip 可写 SSIP/STIP/SEIP_sw); RO 位忽略. */
          hart->trap._mip_sw = (hart->trap._mip_sw & ~MIP_SW_WRITABLE_MASK)
                             | (v & MIP_SW_WRITABLE_MASK);
      }

    并发: _mip_sw 是 plain uint32_t (本 hart 单线程访问 — M-mode csrw mip /
    S-mode csrw sip 都是本 hart guest 软件, dispatcher 读也是本 hart loop 顶);
    异步源在各自模块内自己 _Atomic (CLINT 已 atomic; 未来 PLIC). 跨 hart inject
    SSIP 走 IPI 路径 (远 hart 写 clint.msip → 目标 hart MSIP trap → 目标 hart
    M-handler 自己 csrw mip 设 SSIP), 仍是本 hart 写自己 _mip_sw, 不存在跨 hart
    直接写本字段的路径。csr_mip_read 合成路径 = plain 读 _mip_sw + atomic_load
    各异步源 + 按位 OR — 无 atomic RMW 需求。
    SMP/H/AIA: H 扩展 (Hypervisor 跨虚拟 hart inject) / AIA 扩展 (IMSIC MSI 直接
    写远 hart pending) 会破坏 "本 hart 单线程访问 _mip_sw" 前提, 真做时改 _Atomic
    + atomic 路径. trap.h _mip_sw 字段定义处加 // SMP/H/AIA: 注释占位.


--------------------------------------------------------------------------------
适用范围
--------------------------------------------------------------------------------

本协议适用于所有 csr 字段, 不限 trap_csrs_t:

  - trap_csrs_t (cpu.h 内嵌, trap.h 定义)
      _mstatus / _medeleg (类 1) / mideleg (类 3) / _mie (类 (2a)) / _mip_sw (类 5) /
      xtvec[4] / xepc[4] / xcause[4] / xtval[4] / xscratch[4] 等

  - cpu_info_per_hart_t (cpu.h)
      per-hart 私有 RO csr (mhartid / misa); 严格说不属于上面四类 cover 范畴 (本协议
      管"共用同一物理字段的视图/投影"); per-hart 私有字段直接命名 (不加前缀)

  - cpu_info_shared_t (cpu.h)
      多 hart 共享 RO csr (mvendorid / marchid / mimpid); 同上, 不需前缀

  - 未来 fcsr (isa/fpu.h)
      _fcsr 类 (1)+(2a) 特殊 — RV spec 规定 fcsr 32 位; csr 入口 fcsr / fflags / frm 共享
      物理字段, fflags 和 frm 是 fcsr 的 sub-view (跟 sstatus 是 _mstatus 的 sub-view 同
      形态)。命名 "_" 前缀。

  - 未来 vector csr (isa/vector.h)
      混类:
        _vcsr 类 (1)+(2a) 特殊 — vcsr / vxsat / vxrm 共享物理字段 (跟 _fcsr 同形态);
              命名 "_" 前缀。
        vstart / vtype / vl 类 3 — 各自单字段单 csr 入口, 不带前缀。


--------------------------------------------------------------------------------
为什么这样命名
--------------------------------------------------------------------------------

  (1) 看到字段名就知道访问形态
      - _foo:        物理 64 位 (类 1) 或单纯多入口看 mask 子集 (类 2a); read/write
                      helper 用 mask/shift 操作单一物理 source
      - xfoo[4]:     priv 索引 (类 4), helper 用 [PRIV_M] / [PRIV_S] 区分 csr addr
      - foo:         单一独立字段 (类 3, helper 直读)
      - _foo_sw / _foo_hw: 物理字段是 csr 入口的可写子集 (类 5; 不是完整 csr source);
                      read 时 OR 异步源 / compute 派生 = 完整 csr readout; write 只动
                      字段对应位 (其他位由源驱动)

  (2) 跟 RV 手册风格对齐
      手册用 xepc 同时指代 mepc / sepc; 项目代码 xepc[4] 直接对应

  (3) future-proof RV64
      _mstatus / _medeleg 等 64 位字段在 RV32 拆 csr 入口访问, RV64 时直接 64 位整体
      访问; 字段类型不变 (uint64_t), 改的只是 csr 入口形态


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不规定字段在 struct 内的顺序 / 对齐 / padding
  - 本协议不规定 RO/RW/WARL 行为 (那是 csr.c 各 helper 自己的事)
  - 本协议不规定 cpu_info_per_hart_t / cpu_info_shared_t 的命名 (per-hart vs
    shared 是另一维度的划分; 不属本协议四类)


================================================================================
## §7. 多线程 vs 多 HART 术语
================================================================================

涉及文件:
  - src/debug.h           (镜像本节内容; 两边都看, 内容一致)
  - src/core/cpu.h        (cpu_t / cpu_info_per_hart_t / cpu_info_shared_t 拆分体现)
  - src/platform/clint.h  (未来 — clint.mtime / clint.mtimecmps[N] shared 字段示例)
  - src/jit/smc.h         (未来 — page_dirty bitmap shared 字段示例)
  - src/jit/jit_cache.h   (未来 — jit_cache 表头 shared 示例)
  - 任何引入 host pthread 的模块 (timer / monitor / hart 线程本体)


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

从 a_02 起项目开始涉及辅助线程 (timer / 未来 monitor); "hart 数" 跟 "host thread
数" 不再 1:1 对齐, 之前 single-hart-single-thread 时代隐含的"hart = thread"约定
要正式拆开。本节固定术语, 后续模块 doc / 注释 / commit message 引用同一组词。


--------------------------------------------------------------------------------
术语定义
--------------------------------------------------------------------------------

hart        — RV guest hart (architectural concept)。一个 hart 对应一份 cpu_t,
              SMP 真做时对应一个 host pthread; 跑 guest 指令的"线程实例"。
              hart 数由 guest 视角 (misa / mhartid / RV 配置) 决定, 不由 host
              pthread 数决定。

host thread — OS 级 pthread, 包括两类:
              (a) hart 线程: 每 hart 一个, 持 cpu_t, 跑 dispatcher
              (b) 辅助线程: 不持 cpu_t, 不跑 guest, 只动 shared 数据
                            例 timer 线程 (写 clint.mtime); 未来 monitor 线程
                            (读 perf shm / 暴露调试接口)

数据归属:
  per-hart    : cpu_t (regs / trap_csrs / tlb_table / satp / per_hart_info 等)。
                只本 hart 线程读写, 不需 atomic。
  shared      : clint.mtime / clint.mtimecmps[N] / page_dirty bitmap /
                jit_cache 表头 / 未来 LR/SC reservation table / SV32 PT 内
                PTE.A/D bit (mmu_walk 路径 atomic_fetch_or relaxed; session 024
                落地, 详 mmu.h "为什么 atomic_fetch_or" 段) 等。多 hart 线程
                + 辅助线程都可能读写, 用 C11 atomic (memory_order_relaxed 起步,
                fence 按需加)。
  thread-local: debug.c::trace_buf / trace_idx / hartid_self 等 host trace 状态。
                __thread storage class, 每 hart 线程自动一份独立 buffer; hart 退出
                前 flush 一把到 stderr (DEBUG_NEWLINE 在 dispatcher 退出前触发 +
                hart_exec_run 末尾兜底), 输出带 "[hart%u trace] " prefix 让块
                之间能拎清; 整 hart join 阶段 (trace + perf + halted) 在 halted
                行后加一个 EOL 收尾, 跟下一 hart / 销毁阶段视觉分开。timer 辅助
                线程不打 trace, 其 __thread 实例永远为空, 仅占少量 TLS (~4 KB/线程)。


--------------------------------------------------------------------------------
关键约束
--------------------------------------------------------------------------------

(1) "多 hart" ≠ "多线程"。timer / monitor 等辅助线程数不算 hart 数; 它们不持
    cpu_t, 不影响 misa / mhartid 等 hart-counting 属性。
    例: 单 hart + 1 timer 辅助线程 = 1 hart + 2 host threads。

(2) 辅助线程只动 shared 数据, 永远不直接读写任何 cpu_t 字段 (包括 trap_csrs_t /
    tlb / satp / regs)。要拿 guest 状态必须走 hart 线程主动 (例: hart 线程
    自己读 atomic mtime → 跟 mtimecmp 比 → set mip.MTIP bit)。

(3) cpu_t 任何字段保持非 atomic (fast path 性能要求); shared 字段一律 atomic
    (跨线程读写的 host 内存安全要求)。这条契约一旦违反 → C11 data race UB,
    debug 路径不可达。


--------------------------------------------------------------------------------
monitor 模型 (shared 数据接口暴露规则)
--------------------------------------------------------------------------------

上文"数据归属"段决定"哪些字段 atomic"; 本段补充"shared 数据怎么对外暴露"。
来自 Hoare/Hansen 并发 monitor 范式: 每个共享状态模块封装内部 atomic 字段 +
同步细节, 对外只暴露 consumer / producer 接口, 调用方不感知内部 atomic /
memory_order 选择。

(注: 这里的 "monitor" 是并发理论 monitor 范式, **不是**未来 src/monitor/ 目录
里的"监看程序" (perf counter / 外部观察接口)。两个概念中文都译"监视器"易混;
长期 TODO 统一术语 — 真做 src/monitor/ 时拍。)

项目内 monitor 实例:

  clint = 完整 monitor (第一个)
    内部状态: _Atomic uint64_t mtime / mtimecmps[N] / msip[N] + pthread_t
              timer_thread
    内部 actor: file-static timer_run routine (不算外部)
    对外 consumer: is_clint_msip_pending / is_clint_timer_pending / clint_read
                   (bus MMIO)
    对外 producer: clint_write (bus MMIO)
    lifecycle: clint_init / clint_reset / clint_destroy

  plic = monitor 但无辅助线程 (atomic 字段做 hot path 优化, set/clear 同步 wrlock)
    内部状态: pthread_rwlock_t 保护的 plic struct (sources/contexts/plic_ctx_map) +
              独立 file-static atomic 子集 2 个 (跟 rwlock 区, atomic 自带 ordering 不
              持 lock): _Atomic int plic_ctx_eip[PLIC_N_CONTEXTS] (per-ctx visible-
              pending boolean, csr_mip_read hot path 用) + _Atomic uint32_t
              plic_pending_bitmap_cache[(PLIC_N_SOURCES+31)/32] (MMIO pending bitmap
              区 word cache, guest lw 0x0C00_1000 用)
    对外 consumer: is_plic_meip_pending / is_plic_seip_pending (热路径
                   atomic_load(plic_ctx_eip[ctx_id], acquire) 直返, 零 lock) /
                   plic_read (bus MMIO; pending 区 atomic_load(plic_pending_bitmap_
                   cache[word_idx], acquire) 直返零 lock; priority/threshold/enable
                   仍持 rdlock; claim 持 wrlock)
    对外 producer: device_set_pending / device_clear_pending (同步 wrlock + 改
                   sources[].device_line + recompute_ctx_eip atomic_store +
                   recompute_pending_bitmap atomic_store + unlock; 跨线程调用
                   同 wrlock 短临界区) / plic_write (bus MMIO; wrlock 内顺手
                   recompute, 保持两个 atomic cache 反映最新 effective)
    lifecycle:    plic_init / plic_reset / plic_destroy (单 rwlock, 无锁顺序问题)
    设计要点:     hot path 优化的本质 = atomic 字段 (plic_ctx_eip /
                   plic_pending_bitmap_cache), 让 dispatcher 主帧 is_plic_*_pending
                   走 atomic_load 直返, 零 lock 零 scan。wrlock 路径同步维护 atomic
                   字段, 跟真硬件 wire 模型对齐 (设备 ACK + complete 同 cycle, 没
                   异步 staleness window).
    演进 trail:   曾试过 refresh queue + thread 让 device_line 改异步, 撞 handler
                   同步 ACK + 异步 CLEAR race 引起的 spurious re-fire 回退. 详
                   plan §1.26 + trade_off_log §T.6 + a_03_review.md trail (A).

  uart = 完整 monitor + reader + tx_drain 双辅助线程 (异步默认体例对仗 virtio_blk)
    内部状态: pthread_mutex_t 保护的 uart struct (8 寄存器 + RX FIFO + TX FIFO
              UART_FIFO_SIZE 容量 + device_line cache + thr_empty_pending_acked)
              + pthread_cond_t tx_not_empty + 双 pthread_t reader_thread / tx_drain_thread
    内部 actor (2 个):
      uart_reader_run    — RX 路径: poll(STDIN, POLLIN, 100ms) 心跳检 SDS; 命中
                           POLLIN 读 1 byte → push RX FIFO + 重算 device_line
      uart_tx_drain_run  — TX 路径: cond_timedwait(tx_not_empty, UART_TX_DRAIN_
                           INTERVAL_MS=10ms) 兜底 + hart 入 queue cond_signal 立即
                           wake; wake 后锁内拷整 FIFO 到 stack buf + reset
                           tx_count=0 + 清 acked + 重算 device_line (让 ETBEI 中
                           断 fire) → 锁外 write(STDOUT_FILENO, batch); 跟
                           virtio_blk io_worker 同 cond_signal+timedwait 模式;
                           shutdown 残余 drain (不丢字节, 跟 virtio_blk 丢残余请
                           求语义不同)
    对外 consumer: uart_read (bus MMIO; RBR pop FIFO / IIR readout 副作用 ack THR;
                   LSR.THRE/TEMT 真反映 tx_count)
    对外 producer: uart_write (bus MMIO; THR 入 tx_fifo + cond_signal / 满 silent
                   drop / IER/LCR/MCR/FCR/SCR 字段写)
    lifecycle:    uart_init / uart_reset / uart_destroy + 两对 spawn/join 接口
                  (uart_start/join_reader_thread + uart_start/join_tx_drain_thread)

  runtime = degenerate monitor (单 flag 简化)
    extern _Atomic int runtime_system_reset_signal / runtime_shutdown_signal,
    直接读写无封装函数; 单字段无跨字段一致性问题, 不强制接口函数

memory_order 配对规则:
  producer (write): memory_order_release
  consumer (read):  memory_order_acquire
  建立 happens-before (类比 monitor 范式中 mutex unlock/lock 的顺序)。选择
  封装在模块 .c 内, 模块外不感知。

边界规则 (跨模块):
  外部模块 (csr.c / dispatcher.c / bus.c 等) 不直接 atomic_* 操作 clint 内部
  字段, 一律走 clint.h 接口 (例 is_clint_*_pending 而非裸 atomic_load(&clint.
  msip[N]))。runtime extern flag 是 degenerate case 例外 (单字段)。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不规定 host pthread 怎么创建 / join / cancel (那是 main.c / 各模块
    init 的事)
  - 本协议不规定 atomic 的具体 memory_order (各 shared 字段 sheet 自定; 默认
    起步 relaxed)
  - 本协议不规定"per-hart"还是"shared"的具体边界 (这是各字段 sheet 的事;
    边界改动要写明)


================================================================================
## §8. PMP / MMU / 内存 (RAM + MMIO) 三层关系
================================================================================

涉及文件:
  - src/core/mmu.{c,h}        (地址翻译层, GVA → PA + SV32 PTE 权限)
  - src/platform/ram.{c,h}    (RAM 直通层, PA → host_ptr 偏移)
  - src/platform/bus.{c,h}    (MMIO 派发层, PA → device read/write)
  - src/isa/lsu.{c,h}         (load/store 调度层, 把上面三层串起来)
  - 未来 src/platform/pmp.{c,h} (PA 物理权限层, R/W/X 过滤; v1 不实装, 长期
                                  也不打算实装)


--------------------------------------------------------------------------------
背景
--------------------------------------------------------------------------------

项目早期 (a_02 起步讨论中) 曾把"设备能否被取指 / 读 / 写"这一组语义误归到
device 接口里 — 想象 device struct 持 read_fn / write_fn / execute_fn 三个槽,
NULL 表示不支持。讨论澄清后发现这是把三个独立维度搅在了一起: 一个 device
被允许 R / W / X 这件事既不是 device 自身的属性, 也不是 bus 的职责, 而是
guest OS 通过 PMP 配的物理权限策略。

本节固定 mmu / pmp / 内存 三层的职责边界, 让后续模块设计不再回到这个误解。
顺带记录: 把维度拆清后, PMP 在本项目里既不阻塞 v1, 也不阻塞 v2+, 估计长期
不会实装 — 主流 guest OS 不依赖 PMP 才能起来。


--------------------------------------------------------------------------------
三层职责
--------------------------------------------------------------------------------

(1) 地址翻译层 = mmu (含 TLB / walker)
    职责: GVA → PA + 页级权限检查 (SV32 PTE.R/W/X/U + mstatus.SUM/MXR)
    输入: GVA, perm (R/W/X), priv
    输出: PA (成功) 或 page fault (cause 12/13/15)
    实现: SV32 走 TLB + walker; BARE 是 identity 短路, 不查 PTE
    不知道: PA 落 RAM 还是 MMIO; device 信息; PMP 状态

(2) PA 物理权限层 = pmp (未来; 项目长期不实装)
    职责: 对已翻译 PA 做物理层 R/W/X 过滤 — 跟 device 类型无关, 跟 OS 配的
          PMP CSR 状态直接对应
    输入: PA, perm
    输出: OK 或 access fault (cause 1/5/7)
    实现: 查 PMP CSR (pmpcfg0..15 + pmpaddr0..63) 线性匹配 R/W/X
    不知道: device 信息; PTE 信息; mmu 状态
    项目状态: v1 + 长期不实装 — 主流 guest OS (Linux / FreeRTOS / OpenSBI)
              不依赖 PMP 起 boot; 真接 PMP 是 plan §2 范围以外的优化项

(3) 内存访问层 = ram + bus
    职责: 已通过 (1) 和 (2) 后, 把 PA 真正解到 host 端读写 (RAM 直通 host_ptr
          或 MMIO 派发 device read/write)
    输入: PA, perm, value/buf, size
    输出: load 返回值 / store 副作用 / 无 device → access fault
    实现:
      - IS_GPA_RAM(pa)  → gpa_to_hva_offset + pa, 直通 host_ptr memcpy
                          (load 直接 *hva 返回; store 走 store_helper, HVA-based,
                          含 LR/SC + 未来 SMC 副作用入口)
      - 否则 → mmio_read_helper / mmio_write_helper(hart, pa, gva, ...)
              → bus 线性扫表 + device read/write fn
      - bus 未命中 → bus 自产 CAUSE_LOAD/STORE_ACCESS_FAULT (5/7) +
                     trap_raise_exception (_Noreturn-on-failure)
    不知道: GVA (作 tval 透传, 不参与派发); priv; PMP 状态


--------------------------------------------------------------------------------
组合形态 (load 路径示例; store / fetch 同形态, perm 不同)
--------------------------------------------------------------------------------

guest 一条 lw 指令的完整翻译路径 (抽象层; 完整调用拓扑见 src/isa/lsu.h 顶段):

  interpreter LOAD case
    │
    ├─ misalign check (LOAD_MISALIGN_CHECK 宏, case 入口 gva 级)
    │      失败 → trap_raise(cause 4 load addr misaligned, tval=gva)
    │
    └─ lsu_load_helper [inline 顶层]
         ├─ BARE: IS_GPA_RAM(gva) ? *hva inline : mmio_read_helper(...)
         ├─ SV32 TLB hit: return *(entry->host_ptr + offset)
         └─ SV32 miss: mmu_walker_helper_load
                       ├─ (1) mmu_walk → PA + pte_wb 建议 set A
                       │      失败 → trap_raise(13 page fault)
                       ├─ (2) pmp_check  [v1 跳过]
                       └─ (3) memory:
                              IS_GPA_RAM(pa) ? 写回 PT + fill TLB + *hva
                                             : mmio_read_helper (不写回 PT,
                                                                 不 fill TLB)

fetch 路径 (mmu_translate_pc) 对称: perm = X, 失败 cause = 12 / 1; 当前没有
"可 fetch 范围表", 故 (3) 阶段是 IS_GPA_RAM 直通 + 否则 access fault (取指
不进 mmio_*_helper — bus 派发到 device 取指无意义, 见 mmu.h "PA 落 MMIO 时的
行为差异" 段)。未来若真做 ROM / flash, 在 (3) 阶段加"可 fetch 范围表"查询,
不动 mmu / pmp / device 接口。

store 路径 perm = W, 跟 load 形态对称但 SV32 TLB hit 也必走 store_helper
(LR/SC + 未来 SMC 副作用强制经 helper, 见 §1 末段 "load / store 不对称")。
mmu_walker_helper_* 一族的颗粒度设计见 §10。


--------------------------------------------------------------------------------
为什么 device 接口里不放 R / W / X / execute 字段
--------------------------------------------------------------------------------

历史误解: 把"该 device 是否允许被读 / 写 / fetch"当成 device 自身能力, struct
持 read_fn / write_fn / execute_fn 三个槽, NULL 表示不支持。

实际形态: 上述三件其实分属三个独立维度, 不在同一层:

  - "该 PA 是否允许 R/W/X" = 权限维度 → 层 (2) PMP, 由 OS 配 PMP CSR 决定;
    跟该 PA 上是 CLINT / UART / RAM 完全无关 (PMP 只看 PA, 不看 device 类型)
  - "该 PA 是否有 host_ptr 可让解释器顺序读字节 (执行)" = 物理可 fetch 维度
    → 层 (3) memory 内部细分 (RAM-like 直通 vs 纯 MMIO 派发); 跟 OS 无关,
    跟 device 类型有关 (CLINT 没 host_ptr, RAM 有), 但不在 device struct 字段
    里, 而在 IS_GPA_RAM 宏 / 未来"可 fetch 范围表"里
  - "该 device 收到 read/write 后做什么副作用" = device 语义维度 → 在 device
    自己的 read_fn / write_fn 实现里, 跟权限无关

device struct (mmio_dev_t in bus.h) 只承担第三件, 是 bus 接口最小化设计 —
read_fn / write_fn 表达"收到访问做什么副作用", 不表达"是否允许被访问"。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不规定 PMP 的具体 region 数 / cfg 编码 (真做时按 RV spec §3.7;
    项目当前没这个计划)
  - 本协议不规定"可 fetch 范围表"的具体形态 (bus 模块未来扩展时定; 当前
    bus.h 注释占位)
  - 本协议不延伸到 IOMMU / PASID 等高级 IO 翻译 (不在 v1 / 长期范围)

## §9. CAUSE_INST_ADDR_MISALIGNED 产生路径 + "0=成功" 接口约定
================================================================================

涉及文件:
  - src/core/dispatcher.c   (循环顶兜底 pc IALIGN 检查 — single source)
  - src/core/interpreter.c  (jal/jalr/branch + mret/sret 自检占位; 实际 dead code)
  - src/core/mmu.{c,h}      (mmu_translate_pc 接口 "0=成功")
  - src/core/trap.c         (trap_set_exception_state 服务的三条 exception 路径)
  - src/platform/bus.{c,h}  (device 接口约定 "0=成功"; bus 自己 _Noreturn)
  - src/platform/clint.c + 未来其他 device  (read/write fn 返回 cause)


--------------------------------------------------------------------------------
背景
--------------------------------------------------------------------------------

CAUSE_INST_ADDR_MISALIGNED = 0 (RV spec exception code 0) 跟项目内 "返回 0 =
成功" 的约定在数值上看似冲突 —— 但实际 cause 0 只在两条专用路径产生, 永远
不经 bus / device / mmu 接口的 return code, 所以 "0=成功" 无歧义。


--------------------------------------------------------------------------------
cause 0 的两条产生路径
--------------------------------------------------------------------------------

(a) 转跳指令自检 (interpreter / 未来 JIT 翻译产物)
    jal / jalr / branch / mret / sret 等写 pc 的指令, 在写之前检查目标地址
    IALIGN 对齐。项目 IALIGN=16 + jal/branch encoding 强制 imm[0]=0 + jalr
    内 & ~1u mask LSB, 实际是 dead code; 保留占位让 IALIGN=32 切换时只改宏
    不改逻辑。

(b) dispatcher 循环顶兜底 (block 1 之前, single source)
    无论 pc 怎么来 —— cpu_create 初始化 / 上一轮 block 出口 / sigsetjmp 跳回
    后的 xtvec / 未来 reset_vector / mret/sret 写的 mepc/sepc 等 —— fetch
    之前在 dispatcher 主循环顶兜底:

        if ((hart->regs[0] & IALIGN_MASK) != 0) {
            trap_set_exception_state(hart, CAUSE_INST_ADDR_MISALIGNED,
                           /*tval*/hart->regs[0]);
            continue;
        }

    位置: 迭代头扫尾 + DEBUG_REFETCH 之后, block 1 之前 —— pc 不对齐时
    regime / TLB / mmu_translate_pc 都没必要算。

    这条是 single source: 任何写 pc 的路径出错都在这里捕。

(a) 是规范层"指令自检"占位 (dead code, 不依赖); (b) 是 host emulator 安全
兜底 (真正捕异常 pc 的路径)。


--------------------------------------------------------------------------------
"0=成功" 接口约定
--------------------------------------------------------------------------------

跟 mmu_translate_pc 同形态, 项目内多个接口共用 "0=成功 / 非0=cause" 编码:

  - mmu_translate_pc(hart, current_tlb, ...) → int
      0    = 成功 (pa_out / hva_out 已填)
      非 0 = trap 已 deliver (trap_set_exception_state 返非0; 见 §1 路径 2b)

  - mmio_dev_t.read / write fn → int
      0    = 成功
      非 0 = cause (RV spec exception code; 例 4/5/6/7)
      device 内部决定 cause 细分; mmio_*_helper 透传给 trap_raise_exception。

  - mmio_read_helper / mmio_write_helper 本身是 _Noreturn-on-failure (失败 longjmp),
    不返回 cause 给调用方 —— 因为调用方 (lsu / mmu walker) 已经在 helper
    深处, 直接 longjmp 比 propagate cause 简洁。

cause 0 (CAUSE_INST_ADDR_MISALIGNED) 不会作为 return code 出现 —— 它只走
上面 (a)(b) 两条路径直达 trap, 不经任何返回值通道。


--------------------------------------------------------------------------------
本质规则: 长跳 vs 返回机制的分界
--------------------------------------------------------------------------------

trap_set_exception_state vs trap_raise_exception 的选择依据:

  - 在 dispatcher 主帧内, 还未进解释器 / JIT  →  trap_set_exception_state (返回机制)
    + 上层 continue 让 while(SRS == 0) 接管。栈帧浅, longjmp 是多余副作用。
    例: mmu_translate_pc fetch fault (§1 路径 2b); dispatcher 循环顶 pc
        IALIGN 兜底。

  - 已进入解释器 / JIT block (控制流深处)  →  trap_raise_exception (_Noreturn
    longjmp) 跳回 dispatcher 的 sigsetjmp 落点。栈帧深, longjmp 跳过中间帧。
    例: interpreter op_kind case 内 trap_raise (§1 路径 2a); load_helper /
        store_helper / mmu_walker_helper_* / mmio_*_helper 内 trap_raise。

跟 §1 (sigsetjmp 协议) 是同一件事的两个角度: §1 描述机制 (sigsetjmp 一次性
+ 两条 raise 路径), §9 描述选择依据 (基于"已进 block 没"决定用哪条)。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不规定 cause 0 的 tval 内容 (项目沿 RV spec, tval = 触发 fault 的
    GVA = pc 当前值; 转跳指令自检时 tval = 跳转目标; dispatcher 兜底时
    tval = pc 自身; 都是同一个值)。
  - 本协议不延伸到其他 cause 跟 "0=成功" 的关系 —— cause 1..15 都 ≠ 0,
    跟 "0=成功" 天然不冲突。
  - 本协议不规定 mmio_*_helper 内 "device 拒绝" vs "未命中" 的 cause 区分
    —— device 自决 cause (拒绝时); 未命中由 bus 自产 CAUSE_LOAD/STORE_ACCESS_FAULT
    (5/7), 在 bus.c 实装时定。

## §10. JIT helper 颗粒度 + may-longjmp 边界 + 寄存器保存协议
================================================================================

涉及文件:
  - src/core/mmu.{c,h}      (mmu_walker_helper_load/store + 未来 amo_lr/sc 一族)
  - src/isa/lsu.{c,h}       (lsu_load_helper / lsu_store_helper / store_helper)
  - src/core/interpreter.c  (PRIV_CHECK_OR_TRAP / SYNC_COUNT / LOAD_MISALIGN_CHECK
                             等 file-local 宏)
  - src/core/csr.{c,h}      (csr_op 入口判 priv/RO; may-longjmp 边界)
  - src/platform/bus.{c,h}  (mmio_read/write_helper _Noreturn-on-failure)
  - 未来 src/isa/amo.{c,h}  (LR/SC + 9 个 AMO 各自的 helper 入口)
  - 未来 src/jit/translator.c (emit 时遵守同协议)


--------------------------------------------------------------------------------
(A) helper 颗粒度 by design — 每条 RV 访问指令对应一个 helper 入口
--------------------------------------------------------------------------------

mmu_walker_helper_load / store (现有) + mmu_walker_helper_amo_lr / amo_sc /
amo_* (未来) 这一族函数, **不只是 TLB miss 时的 fallback**, 而是 by design
给 **JIT 块出口** 准备的"不同颗粒度的助手函数":

  1. JIT 翻译块内每条访问指令 emit `call mmu_walker_helper_xxx` = 块边界 +
     longjmp 出口 —— **颗粒度 = 单条指令**, 函数地址静态绑定到 emit 出来的
     call 指令
  2. 不能合并成"统一 mmu_walker_helper(op_kind, ...)" 大入口 —— 大 helper
     需要在 helper 内 switch on op_kind, 多一层间接 + JIT 翻译产物里无法
     静态绑各种 inline 特化 + 调用约定也得跨 op_kind 一致 (限制 helper
     实现的灵活性)
  3. → 未来 LR/SC + 9 个 AMO 各需要自己的 mmu_walker_helper_amo_xxx, 不能
     图省事合并; 这条决定 isa/amo.{c,h} 接口设计 + JIT translator emit 路径表

同样原则也应用到 lsu 层: lsu_load_helper / lsu_store_helper (顶层 inline)
+ 未来 amo_lr_helper / amo_sc_helper / amo_xxx_helper 各自入口, 不合并。


--------------------------------------------------------------------------------
(B) may-longjmp 边界列表
--------------------------------------------------------------------------------

"may-longjmp 边界" = 调用后可能不返回 caller (内部 trap_raise_exception
_Noreturn longjmp) 的位置。本项目当前 may-longjmp 边界:

  解释器 / JIT 控制流深处 (§1 路径 2a):
    - lsu_load_helper / lsu_store_helper        (顶层 inline; SV32 miss 调
                                                 walker; BARE MMIO 调 bus)
    - mmu_walker_helper_load / store            (SV32 miss 走 mmu_walk + 调
                                                 lsu / bus)
    - store_helper                              (HVA-based, RAM 写 + LR/SC +
                                                 SMC 副作用; 不直接 longjmp,
                                                 但调链可能)
    - mmio_read_helper / mmio_write_helper      (bus _Noreturn-on-failure)
    - csr_op                                    (入口判 priv / RO 写违法 →
                                                 trap_raise)
    - trap_raise_exception                      (本身就是 _Noreturn 长跳入口)
    - PRIV_CHECK_OR_TRAP (file-local 宏)        (MRET / SRET / SFENCE.VMA 等
                                                 priv 不够 → trap_raise)
    - LOAD_MISALIGN_CHECK / STORE_MISALIGN_CHECK (case 入口 gva 级查 → trap_raise)
    - 未来 amo_*_helper / amo_walker_helper_*   (同 lsu 形态)

  dispatcher 主帧内 (§1 路径 2b, **不长跳**):
    - mmu_translate_pc                          (fetch 失败 trap_set_exception_state +
                                                 return; 不长跳)
    - dispatcher 循环顶 pc IALIGN 兜底           (trap_set_exception_state + continue;
                                                 §9 (b))


--------------------------------------------------------------------------------
(C) 寄存器保存协议 (JIT translator 配合)
--------------------------------------------------------------------------------

§1 中段已规定 "Translator 配合机制 (寄存器保护)": **emit 每个 may-longjmp
helper call 之前, store 所有映射 host 寄存器到 cpu_t**。本节是具体应用清单。

(B) 列出的每个 may-longjmp 边界, JIT translator 都要在 emit call 之前插
寄存器保存序列 (跟 csr_op / lsu_*_helper / mmu_walker_helper_* 同处理)。
没有例外, 没有"这个 helper 不会 longjmp 所以省了"的标注 — 见 §1 "统一保护
vs 标注式" 的策略选择。

→ 解释器视角与 JIT 视角的对偶:

  解释器:  SYNC_COUNT() 宏在 may-longjmp 调用前同步 count_out
           (RV precise trap 要求"触发指令不算入" — failing 那条不能被
            cumulative count 累上, 否则 dispatcher 用旧 count 算错)

  JIT:     emit "store 所有映射 host 寄存器" 序列在 may-longjmp call 前
           (寄存器值要在 longjmp 跳走前固化到 cpu_t, 否则 sigsetjmp 落点
            读到的是旧值)

两者是同一哲学的两个版本: "may-longjmp 边界前, 把瞬态状态固化到 cpu_t"。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本协议不规定 helper 内部具体 trap cause 细分 (cause 集见 §1 + 各 helper
    自身 doc)
  - 本协议不规定 JIT 寄存器映射策略 (是 translator / backend 内部决定)
  - 本协议不延伸到 IRQ 中断分发 (T3+ 真做中断时, "中断走长跳还是返回机制"
    再扩 §9 + 本节)

## §11. predicate 函数命名约定
================================================================================

涉及文件:
  - src/platform/clint.{c,h}::is_clint_msip_pending / is_clint_timer_pending
  - src/core/decode.h::is_block_boundary_inst (static inline; 已符合)
  - 未来任何返 0/1 状态查询函数


--------------------------------------------------------------------------------
约定
--------------------------------------------------------------------------------

返 0/1 (布尔语义) 的查询函数 — 谓词 (is / has) 前置, module 嵌入 descriptor
后段:

  - is_<module>_<thing>_<state>     例: is_clint_msip_pending
  - is_<thing>                      例: is_block_boundary_inst (本地 static inline)
  - has_<module>_<thing>            例 (假想): has_jit_cache_hit

哲学:
  - 谓词位置高于 module prefix, 因为 predicate 是函数的语义关键词; module
    是次要 namespace 信息。读起来 "is + 谁的 + 什么状态" 自然。
  - CLAUDE.md 通用 schema `module_verb_object` 不覆盖 predicate 形态 — 本节
    是补充规则, 不替代 schema。非 predicate 函数仍走 schema (例 clint_init /
    clint_reset / clint_destroy)。
  - 项目不用 bool, 返 int (0/1)。跟 §9 "0=成功 / 非 0=cause" 接口约定的布尔
    语义不冲突 — 那条针对 RV exception cause 编码; 本节针对状态查询。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 本节不规定 predicate 函数的副作用 / atomic 性 / longjmp 行为 (各 sheet
    自定)
  - 不规定参数命名 (例 hartid 等参数名各 module 沿用本身约定)
  - 不替代 module_verb_object schema — 非 predicate 函数 (init / reset /
    destroy / read / write / walk / ...) 仍走 schema

## §12. 线程 lifecycle (spawn / join 配对)
================================================================================

涉及文件:
  - src/main.c                (当前所有 host thread 的 spawn / join 责任)
  - src/runtime.{c,h}         (system_reset_signal / shutdown_signal extern flag;
                               runtime_fatal 紧急停机 + wfi_kick_all)
  - src/platform/clint.{c,h}  (clint_start_timer_thread / clint_join_timer_thread 对偶)
  - src/device/uart.{c,h}     (uart_start_rx_thread / uart_join_rx_thread 对偶)
  - src/device/virtio_blk.{c,h} (virtio_blk_start_io_worker_thread /
                                  virtio_blk_join_io_worker_thread 对偶)
  - src/core/wfi.{c,h}        (wfi_kick 点对点唤醒 / wfi_kick_all 紧急叫醒所有 hart)
  - 未来任何 spawn host thread 的模块


--------------------------------------------------------------------------------
背景
--------------------------------------------------------------------------------

引入辅助线程 (timer 累加 atomic mtime) 时确立; 之后 SMP 真做时还会加 hart
线程, 未来 monitor 也可能起线程。本节固定 "谁 spawn 谁 join" 协议, 避免
destroy 函数隐含 pthread_join 导致控制流隐式 block (看 destroy 不知道里面
还会等线程)。

--------------------------------------------------------------------------------
约定
--------------------------------------------------------------------------------

默认 — 线程由谁 spawn 就由谁 (或某个清晰的层级) join。
当前 case: main 调 clint_start_timer_thread 起 timer thread → main 调 clint_join_timer_thread
显式 join, 不埋进 clint_destroy。

函数命名 — spawn / join 对偶函数单独暴露, module_verb_object schema:
  - clint_start_timer_thread             / clint_join_timer_thread          (已实装)
  - uart_start_rx_thread             / uart_join_rx_thread          (已实装)
  - uart_start_tx_thread           / uart_join_tx_thread        (已实装)
  - virtio_blk_start_io_worker_thread    / virtio_blk_join_io_worker_thread (已实装)
  - 未来 hart_start    / hart_join         (SMP 真做时)
  - 未来 monitor_start / monitor_join      (perf shm 接口)

  (注: PLIC 不发线程 — 是 "monitor 但无辅助线程" 第一个完整范例; 曾试过异步
   refresh thread 后回退, 详 trade_off_log §T.6.)

  (注: UART 双线程 reader + tx_drain — RX/TX 都异步, 对仗 virtio_blk io_worker
   的 cond_signal+timedwait 模式; tx_drain join 入口先 cond_broadcast 唤醒立即
   跳出 cond_timedwait 兜底 timeout 再 pthread_join, 不等 10ms tail.)

destroy 函数纯 cleanup — atomic 字段清 / 资源 free 类, **不含 pthread_join**。
跟 init 对偶, 反 init 做的事 (init 做了 atomic 字段初始化 + bus 注册 →
destroy 反过来)。

例外: 模块内部临时异步任务 (模块自己起的) 由模块自己 join, 但要在 sheet 写明
"此线程模块内部 lifecycle"。


--------------------------------------------------------------------------------
唤醒 vs 紧急叫醒 (core/wfi) + runtime → core/wfi 方向依赖
--------------------------------------------------------------------------------

wfi_kick(hartid) — 唤醒**某个**在 WFI cond_wait 的 hart (中断源 CLINT/PLIC
  pending 0→1 翻转时点对点; hart 醒来 re-check predicate 决定继续跑还是接中断)。

wfi_kick_all() — 让**所有** hart 尽快看到 SRS, **紧急停机专用** (唯一调用方 =
  runtime_fatal)。循环用 cap (MAX_HARTS) 不是 n_harts: fatal 是"出大事了", 宁可
  多 kick phantom slot (空 waitqueue 近零成本, glibc 跳 futex syscall; kick 幂等)
  也不漏 kick 真 hart。
  - 正常 shutdown **不**用 kick_all: predicate 第一条已查 SRS + cond_timedwait
    WFI_TIMEOUT_NS (500ms) 兜底自醒, ≤500ms tail 可接受 (a_03 #194/#198 撤所有
    正常调用点; trade_off_log §T.8)。fatal 场景语义相反 ("别睡了立刻停"), tail
    不可接受 → 是 kick_all 唯一站得住的调用点。
  - 未来正常状态下按 n_harts 的 kick_all 需求 (例多 hart 协同), 另分一个函数,
    不复用 wfi_kick_all (它语义已定死为紧急停机)。

runtime → core/wfi 方向依赖: runtime_fatal 调 wfi_kick_all。runtime 本是最底层
degenerate monitor (谁都依赖它、它不依赖别人), 但 fatal 是"贯穿整机的紧急停机
控制流", 调别模块的"紧急停止函数"不破坏 runtime 定位。死锁安全: wfi_kick_all 只
碰 wfi_slots[].mutex, 不回头碰 plic/clint 锁 → 持锁 call site (plic recompute 持
plic.lock) 调入无锁环。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 不规定 SDS / SRS 信号的具体 memory_order (relaxed 起步; §7 monitor 模型
    规则覆盖 — producer release / consumer acquire)
  - 不规定线程优先级 / SCHED_FIFO 等调度策略 (各模块自定)
  - 不规定 cancellation 机制 (项目不用 pthread_cancel / pthread_kill,
    一律 cooperative — atomic flag + worker periodic check + main join)
  - 不教条 — 真有特殊设计场景模块内部 join 也行 (但 sheet 写明)

## §13. 类型规约 (typedef family)
================================================================================

涉及文件:
  - src/riscv.h              (typedef family 4 个定义 + 顶段 doc)
  - src/core/cpu.{c,h}       (regs[32] / satp / per_hart_info / shared_info CSR 字段)
  - src/core/trap.{c,h}      (trap_csrs_t 物理字段 + trap helper 签名)
  - src/core/csr.{c,h}       (csr_op + 各 csr_*_read/_write helper 签名)
  - src/core/mmu.{c,h}       (translate / walker 签名 + 内部 PTE / PA 变量)
  - src/core/decode.{c,h}    (decoded_inst_t.raw_inst + decode() 参数)
  - src/core/tlb.{c,h}       (tlb_e_t.gva_tag)
  - src/platform/clint.{c,h} (mtime / mtimecmp / msip)
  - src/platform/plic.{c,h}  (plic_ctx_eip / plic_pending_bitmap_cache / sources/
                              contexts atomic 字段; 都是 spec-pinned 32-bit per
                              RV PLIC v1.0.0, 跟 XLEN 无关)
  - src/device/virtio_blk.{c,h} (capacity_sectors 是 spec virtio v1.0 §4.2.2.2
                                  Config space 钉死 64-bit; 其他寄存器是 spec
                                  钉死 32-bit, 跟 XLEN 无关)
  - src/isa/lsu.{c,h} / sfence.{c,h}  (helper 签名)
  - 未来任何"宽度有 XLEN / spec 语义"的字段

  (注: a_03 落地的 plic/uart/virtio_blk 实装时未用 typedef family 名 (用裸
   uint32_t / uint64_t), 是 spec-pinned 32/64 不跟 XLEN 动, 切 RV64 不需要
   review; 列在涉及文件里仅作 trail 完整, 不要求批量改 typedef 名.)


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

项目当前 v1 = RV32 单 XLEN (MXLEN = SXLEN = UXLEN = 32 不可变), 没有运行期切
XLEN 需求。但字段大量用裸 uint32_t / uint64_t 写, 看不出哪个跟 XLEN 绑、哪个
spec 钉死 32、哪个 spec 钉死 64。切 RV64 时要逐字段 review, 工作量爆炸。

typedef family 不是引入"真 XLEN 抽象", 是给字段加宽度来源标注 trail —— 看名字
立刻知道字段宽度来源, 切 RV64 时 grep 即可分流"哪个要 review / 哪个不动"。


--------------------------------------------------------------------------------
4 个 typedef (定义在 riscv.h 顶段)
--------------------------------------------------------------------------------

  uxlen_t  (= uint32_t @ RV32; RV64 时改 uint64_t)
    XLEN-tied unsigned, 宽度跟 build target XLEN 走。借鉴 Rust usize。
    用法: 整数寄存器 + pc (regs[]) / MXLEN-bit CSR (xcause / xtval / xepc /
          xtvec / xscratch / mideleg / _mie / _mip_sw / satp / mhartid / misa /
          marchid / mimpid) / GVA / PA。

  ixlen_t  (= int32_t @ RV32; RV64 时改 int64_t)
    uxlen_t 的有符号对偶, 借鉴 Rust isize。family 完整性保留 —— 当前无字段实际
    用到 (decoded_inst_t.imm 留作切 RV64 时连 decode 整体重审, 不提前改)。

  u32_t    (= uint32_t; 切 RV64 不动)
    RV spec 钉死 32-bit, 跟 XLEN 无关。
    用法: Sv32 PTE (mmu.c pte0/pte1, mmu_walk 出参 pte_flags / pte_wb_new) /
          msip (CLINT) / 指令编码 (decoded_inst_t.raw_inst, decode() 参数,
          csr_op raw_inst 参数) / mvendorid。

  u64_t    (= uint64_t; 切 RV64 不动)
    RV spec 钉死 64-bit, 跟 XLEN 无关。
    用法: RV32 物理 64 位 CSR (_mstatus / _medeleg, csr 入口 RV32 拆 32 位访问) /
          mtime / mtimecmp (CLINT)。


--------------------------------------------------------------------------------
跟 stdint uint32_t / uint64_t 的语义差异
--------------------------------------------------------------------------------

  uint32_t / uint64_t = 普通定宽整数, 不约束语义 (host 概念 / index / 位段分解
                        临时 / size 等随便用)。
  u32_t / u64_t       = 项目内部约定 "RV spec 钉死的宽度, 不跟 XLEN 动"。

编译器看 u32_t 跟 uint32_t 是同 alias 不区分; 区别只在人 grep —— grep u32_t 找
"故意 32-bit 不变"的字段, grep uxlen_t 找"切 RV64 要 review"的字段。

阅读者第一次见 u32_t 可能误以为 uint32_t 的简写 —— 这是命名风险, 但跟
uxlen_t / ixlen_t / u64_t 在 family 内表达一致 (短形态)。


--------------------------------------------------------------------------------
类型检查行为 (C typedef = 纯 alias)
--------------------------------------------------------------------------------

C typedef 是纯名字 alias, 不增强类型检查 (跟 Rust `type Foo = u32` 同; 跟 Rust
newtype `struct Foo(u32)` 不同)。uxlen_t / u32_t / u64_t 互相赋值 / 函数参数
互传 / 隐式转换都不警告。

真要 strong typing 在 C 里只能 struct wrapper (struct { uint32_t v; } + .v
访问), 改 codebase 太大、项目规模不补偿成本 —— 不引入。

附加收益: 切 RV64 时 typedef 定义改 (uxlen_t uint32 → uint64), 若 build flag 带
-Wconversion 会自然查出 "uxlen_t (uint64) → u32_t (uint32) 隐式 truncation" 类
bug。注: -Wconversion 当前不在项目 build flag 内, 此收益要等真加该 flag。


--------------------------------------------------------------------------------
切 RV64 工作流
--------------------------------------------------------------------------------

  1. 改 riscv.h 的 typedef 定义: uxlen_t → uint64_t, ixlen_t → int64_t
     (u32_t / u64_t 不动)。
  2. grep uxlen_t / ixlen_t 逐字段 review (这就是 typedef 的真正收益)。
  3. 同步处理 typedef 不覆盖的部分 (本次有意推迟):
     format string (%u / %08x → %lu / %016lx) / decode.c imm·sext·指令编码整体
     重审 / CAUSE_INTERRUPT_BIT 等 mask 宏 / mstatus.SXL·UXL 字段 / tlb_e_t 16B
     布局 (gva_tag 变 8 字节) / CLINT MMIO size=8 路径。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 不引入运行期 XLEN 切换 (v1 = RV32 单 XLEN 不可变)。
  - 不引入 struct wrapper 强类型 (C 无原生 newtype, 成本不补偿)。
  - 不覆盖 host 概念字段 (jmp_buf_ptr / 计数器 / size / host 指针 / pthread_t /
    size_t 等) / enum encoding (priv / op_kind / cause 等) / index (rd/rs1/rs2 /
    asid / hartid / TLB index) / 位段分解临时 —— 这些跟 guest XLEN 无关。
  - 不规定 mask 宏类型 (IRQ_* / CAUSE_* / SIP_MASK 等是 bit pattern 无类型,
    caller 用时按 caller 字段类型 promote)。

## §14. per-hart cache-aligned slot 协议
================================================================================

涉及文件:
  - core/wfi.c        (wfi_slot_t = pthread_mutex_t + pthread_cond_t; WFI 唤醒框架)
  - platform/clint.c  (clint_per_hart_slot_t = _Atomic u32_t mtip + pthread_mutex_t
                       mtip_lock; MTIP 异步 cache)
  - 未来: Sstc stip / F·D fcsr per-hart 缓存等同形态扩展时按本协议


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

015 引入 WFI cond_wait 唤醒框架 + CLINT MTIP atomic cache, 项目第一次出现
"每 hart 一份 atomic 字段 + 同步原语 + 高频跨 hart 读" 的 pattern。两个模块
独立 typedef + 自管数组, 但行为约束一致, 本节钉死跨模块共用体例 — 防 SMP
后 false sharing 性能塌方, 防之后第三个实例 (Sstc) 走偏。

跟 §7 monitor 体例兼容: monitor 是 "模块持 atomic + 锁封状态" 顶层语义, 本节
是其中 "状态按 hart 分槽" 的具体落地形态。


--------------------------------------------------------------------------------
体例 (5 条)
--------------------------------------------------------------------------------

  1. slot struct 末段加 `char _pad[64];`, 整体 `_Alignas(64)`; 保证
     sizeof(slot) ≥ 64B 且按 cache line 对齐, hart i 改自己槽不 invalidate
     hart j 的 reader L1 line (假共享防御)。pthread_mutex_t + pthread_cond_t
     已超 64B → 整体常 ~128B, _pad 仍写但作用退化为"对齐边界"明示。

  2. slot 数组 file-static, 不暴露指针; 接口按 hartid 索引 (uint32_t)。
     cpu_t 不持 slot 指针, 模块自管 (clint_per_hart[hartid] 风格), 跟 §7
     monitor "不暴露内部" 一致。

  3. mutex/cond 在模块 init 时一一 pthread_*_init, destroy 时一一
     pthread_*_destroy; 跟 §12 spawn/join 配对原则同类 (init/destroy 配对)。
     init 失败走 shutdown_signal_set_bit(DEVICE_FAIL) (CLAUDE.md 体例)。

  4. atomic 字段用 _Atomic + atomic_load/store_explicit 显式 memory_order:
     writer release / reader acquire 配对 (跨 hart 写的可见性靠这层, 锁只
     保 reader-side 一致性, 不替代 ordering)。

  5. lock-protected "recompute → atomic_store → 必要时唤醒" 模式跟 PLIC
     rwlock + atomic cache 体例同形 (见 §7 trade_off_log §T.6):
       lock(slot_lock)
       new_val = compute(原子读 inputs)
       old_val = atomic_load(slot.cache, relaxed)
       if old_val != new_val:
           atomic_store(slot.cache, new_val, release)
           if 边沿条件 (0→1 等): wfi_kick(hartid) 或同类副作用
       unlock(slot_lock)


--------------------------------------------------------------------------------
未来扩展
--------------------------------------------------------------------------------

  - Sstc stimecmp: clint 内复制 mtip 路径, 加 _Atomic u8 stip[MAX_HARTS] +
    stip_lock[MAX_HARTS]; 跟 mtip 同处 recompute + kick (推 plan §2 deferred)。
    (注: MAX_HARTS 现已是编译期 cap 语义, 见 §15; 这里数组按 cap 分配正确)
  - F/D fcsr per-hart 缓存: 真需要 cross-hart 观察时按本节体例落地, 否则
    fcsr 是单 hart 私有字段直存 cpu_t 即可
  - PLIC ctx_eip 数组 padding: 当前是 _Atomic u8 紧凑数组。SMP s2 已把 MAX_HARTS
    从 1 切成 cap 语义 (数组按 cap 分配, 见 §15), 但 cache-line padding 防 false
    sharing 仍 deferred — 真起多 hart 多线程 (s3+) 跑 TSan 看 ctx_eip 是否成 false
    sharing 热点时再补 (smp_todo_list F 节调试方法论)。


--------------------------------------------------------------------------------
非目标
--------------------------------------------------------------------------------

  - 不抽 per_hart_t<T> 泛型 / 不开公共 core/per_hart.h 模板。各模块独立
    typedef 保持本地化, 跟 PLIC ctx_eip + rwlock 同等体例 (没有"PLIC slot
    模板"也活得好)。真出现第 3 个实例 (Sstc) 再评估是否提抽公共模板。
  - 不暴露 slot 指针给外部模块。所有访问走模块接口函数 (wfi_wait /
    wfi_kick / is_clint_timer_pending 等)。
  - cache line 大小不抽 BUILD_CACHE_LINE_SIZE 宏。当前 hardcode 64
    (x86_64 / aarch64 主流值); 真上 Apple M (128) / 老 ARM (32) 需要切换
    时再加, 不预测。

## §15. hart 两数模型 (cap = MAX_HARTS / 运行期 n_harts) + 三类越界语义
================================================================================

涉及文件:
  - src/core/cpu.{c,h}        (n_harts 全局; cpu.h extern + cpu.c 定义 = 1u)
  - src/config.h              (MAX_HARTS = 编译期 cap; 当前 8U)
  - src/main.c                (--smp N CLI 解析 + n_harts = smp_req; per-hart
                               pthread spawn/join)
  - src/platform/clint.c      (4 处 MMIO 边界 + recompute_all_mtip 用 n_harts;
                               lifecycle 配对 + 内部 helper 防御边界保 cap)
  - src/platform/plic.c       (phantom drop helper + recompute_all_ctx_eip + plic_init
                               实连线填充用 n_harts; ctx_map/ctx_to_hartid 整张清表 +
                               单 rwlock + 内部 helper 防御保 cap; 反查表 < 0 fatal)
  - src/core/wfi.c            (数组定义 + mutex/cond init/destroy 配对 + kick_all 全 cap)
  - src/runtime.{c,h}         (runtime_fatal 紧急停机 — 第 3 类越界的落地; 详 §5 末段)


--------------------------------------------------------------------------------
背景与目的
--------------------------------------------------------------------------------

SMP 起拆 MAX_HARTS 原有的双重身份 — v1 单 hart 时 MAX_HARTS 同时是 "数组上限"
跟 "实际 hart 数"; 多 hart 起来后必须区分。本节钉死两数模型 + 三类越界语义 +
逐场景 cap-vs-n_harts 判据, 防 s3 真起多线程后边界条件出错 / fatal 假阳性 /
lifecycle 配对错位泄漏。

跟 QEMU MAX_CPUS + -smp 同形态 (编译期上限 + 运行期实际值)。


--------------------------------------------------------------------------------
两数模型
--------------------------------------------------------------------------------

  MAX_HARTS (config.h)  = 编译期 cap。所有 per-hart 静态数组按 [MAX_HARTS] 分配,
                          形态编译期稳定。lifecycle init/destroy 配对必须用 cap
                          (否则 cap 改 8 后 lifecycle 配对错位 → 资源泄漏 / UAF)。

  n_harts   (cpu.{c,h}) = 运行期实际 hart 数。main 解析 --smp N 后写定一次, 之后
                          只读。约束 1..MAX_HARTS。默认 1。
                          - 非 _Atomic: spawn-before-read happens-before 屏障保证
                            多 hart 只读安全 (跟 ram.h host_ram_base 同体例)。
                          - 暴露 = cpu.h extern + cpu.c 全局定义; 不走函数传参 (是
                            进程级运行期常量, 跟 RAM 起点同性质)。
                          - 归 cpu 模块 (hart 数量是 cpu 概念); 不进 runtime
                            (runtime 只管整机 SRS/SDS 线程控制流, 不持 hart 数)。

  phantom hart           = cap 之内未使用的 hart 槽 (idx ∈ [n_harts, cap))。逻辑
                          上不存在; 任何对 phantom 的访问按下面 "三类越界语义"
                          其中一类处理 (谁是访问者决定走哪类)。


--------------------------------------------------------------------------------
三类越界语义 (按 "谁是访问者" 分)
--------------------------------------------------------------------------------

第 1 类 — guest 经 MMIO 访问 idx >= n_harts 的 CLINT hart
  - 性质: guest 软件 bug (越界访问 reserved hart)
  - 回应: 返 RV access fault (CAUSE_*_ACCESS_FAULT), trap 回 guest; 不拖停模拟器
  - 原因: 否则 buggy guest 可 DoS host
  - 落地: CLINT 4 处 MMIO 边界 (read msip/mtimecmp + write msip/mtimecmp) 用
    `if (idx >= n_harts) return CAUSE_*_ACCESS_FAULT;`, return 在碰字段 /
    atomic_store / wfi_kick / recompute 之前 → 无副作用

第 2 类 — guest 经 MMIO 访问 PLIC 的 phantom ctx (对应 hart >= n_harts)
  - 性质: guest 软件 bug (跟第 1 类同源, 但 PLIC 历来对 region 内越界/reserved
    是 silent ignore 政策, 跟 QEMU sifive_plic 对齐)
  - 回应: silent drop — read 返 0, write 丢; 不 fault, 不 set 字段, 不进仲裁,
    不触发 recompute
  - 落地: helper `plic_ctx_is_phantom(ctx_id)` = `plic_ctx_to_hartid[ctx_id] < 0`
    (phantom hart 槽 plic_init 保持 -1)。落点:
       plic_write enable  — 硬前置 (phantom enable 不写进 → phantom ctx eip 永不
                            0→1 → 不会撞第 3 类的 fatal)
       plic_write threshold / complete — 纵深防御
       plic_read claim / threshold      — 纵深防御 + 不进仲裁
    plic_read priority / pending / enable 按 source/word 索引 (跟 hart 数无关),
    不需 phantom drop。

第 3 类 — emulator 内部读反查表 plic_ctx_to_hartid / plic_ctx_map 读到 -1
  - 性质: 真 emulator bug (存在的 ctx / hart 丢了硬连线 = 内部一致性违例, 跟
    guest 无关)
  - 回应: loud fatal — 调 runtime_fatal(where, detail, bad_value) (详 §5 末段;
    where 传 __func__ 让编译器维护); fprintf 诊断 + SDS+SRS 各 set INTERNAL_FATAL
    bit + wfi_kick_all 紧急叫醒所有 hart
  - 约束: non-_Noreturn / 不 abort — 某些 call site (plic.c recompute_ctx_eip)
    持 wrlock 调入, abort/longjmp 会带锁跳走死锁; call site 在 fatal 后正常返回
    让栈 unwind 出锁, 并自行 return / 跳过副作用 (防 -1 二次越界索引)
  - 落地:
       plic_recompute_ctx_eip_locked      — h<0 调 fatal, 不 else kick (持 wrlock)
       is_plic_meip_pending               — ctx<0 调 fatal, return 0 防二次负索引
       is_plic_seip_pending               — 同上 (注: 隐含 "调本函数 = S-capable
                                            hart" 假设; 当前所有 hart 都 MSU 成立,
                                            未来 hart heterogeneity 引入时回看)

`-1` 哨兵在 "填表/init" 层仍合法保留 (phantom hart 槽 = -1 + U/VS 槽 = -1);
只在 "使用" 层遇到才 fatal — 区分 phantom 还是 emulator bug 由调用上下文决定
(第 2 类 phantom drop 帮 plic_write 路径不会让第 3 类发生)。


--------------------------------------------------------------------------------
cap-vs-n_harts 判据 (新代码加哪边的判据)
--------------------------------------------------------------------------------

用 cap (MAX_HARTS):
  - 数组定义 / 字段长度 (clint.{mtimecmps,msip}[MAX_HARTS], clint_per_hart
    [MAX_HARTS], wfi_slots[MAX_HARTS], plic.plic_ctx_map[MAX_HARTS*4],
    plic.plic_ctx_to_hartid[PLIC_N_CONTEXTS = MAX_HARTS*2]) — 编译期形态稳定
  - lifecycle 配对循环 (init/destroy mutex/cond, init/destroy 填哨兵) — 必须 cap,
    漏一个 → cap 改 8 后泄漏 7 把锁 / 7 个 slot 未清; s2 测不出, s3 才爆
  - 内部 helper 防御边界 (is_clint_*_pending / is_plic_*_pending / wfi_wait /
    wfi_kick 防御 hartid 越界) — hartid 来自 cpu_t wired 不是反查表 -1, 跟第 3
    类正交; 不改 fatal
  - wfi_kick_all 循环 — 紧急停机专用, 宁可多 kick phantom 空 slot (近零成本)
    也不漏真 hart; 详 §12 末段
  - phantom 判定的根表清空 (plic_init 全 -1 填 ctx_map + ctx_to_hartid) — 整张
    表清, 用 cap

用 n_harts:
  - 存在性遍历 (clint_recompute_all_mtip, plic_recompute_all_ctx_eip_locked 用
    `2*n_harts`) — 只算存在的 hart, 省 phantom 空转 + 避免 spurious kick 空 slot
  - 实连线填充 (plic_init 给真实 hart 填 ctx_map + ctx_to_hartid) — phantom hart
    的槽留 -1 = phantom 判定的根
  - 第 1 类 MMIO 边界 (clint 4 处 `if idx >= n_harts return fault`) — guest 视角
    "idx 之外的 hart 不存在"
  - 第 2 类 phantom drop (隐式: plic_ctx_is_phantom 间接判 n_harts 内/外)


--------------------------------------------------------------------------------
SMP s1/s2/s3 落地链路 (trail; 行为恒等变换 → cap 放开 → 真起多线程)
--------------------------------------------------------------------------------

s1 (CLI 解析): --smp N CLI parse + 1..MAX_HARTS 校验; n_harts 默认 1。

s2 (cap-vs-n_harts 判据全场景落地, 行为恒等验收): 把每处边界判据用上节 "cap-
vs-n_harts 判据" 拍正确, main 阶段性钳死 `n_harts = 1u` 忽略 --smp 解析值;
config.h MAX_HARTS 仍 1U。此时:
  - n_harts == 1 == MAX_HARTS → `for i<n_harts` ≡ `for i<MAX_HARTS`,
    `idx>=n_harts` ≡ `idx>=MAX_HARTS`, `2*n_harts (=2)` ≡ `PLIC_N_CONTEXTS (=2)`
  - phantom 判定 plic_ctx_is_phantom 永返 false (ctx 0/1 都被填实)
  - 第 3 类 fatal 永不触发 (ctx_to_hartid 没有 -1 项可读)
  - 全量存量 fixture 100% 绿 + 输出逐字节一致 = s2 验收信号
  - 行为恒等变换成立的前提: "cap-vs-n_harts 判据" 全场景判对 (尤其 lifecycle
    配对没误用 n_harts; 漏在 s2 不可见, s3 cap 改 8 才爆 → s2 是测不出的雷)

s2 末步 (cap 放开): config.h MAX_HARTS 1U → 8U + 删 main 钳死; 此时 n_harts 仍
默认 1 → 单核仍恒等; 用 --smp 2 等手测 cap 放开后多核数据结构就位 (真起多线程
是 s3, 本步只验数组 / 边界 / init 在 cap=8 下不崩 + 单核不回归)。

s3 (真起多线程, 已落地): main 循环 cpu_create n_harts 个 + per-hart dispatcher
pthread spawn/join (file-static hart_exec_run wrapper + harts[MAX_HARTS] +
hart_threads[MAX_HARTS]) + dump 打 hartid。n_harts 写为 smp_req (解钳); spawn
失败走 SYSRESET_BIT_HART_SPAWN_FAIL 进 ABORT_MASK; kick_all 仍专用紧急停机不动
(未来正常状态 n_harts kick_all 需求另分函数, 详 §12 末段)。

================================================================================
## §16. LR/SC reservation 协议 (c 主方案; per-PA hash 锁 + per-hart atomic 数组)
================================================================================

涉及文件:
  - isa/lrsc.{c,h}        (reservation 数据 + 函数族; bucket lock 数组)
  - isa/lsu.c             (store_helper 末段 #5)
  - isa/amo.c             (9 apply 末段 #6)
  - isa/fence.c           (fence_i_helper #4)
  - isa/sfence.c          (sfence_vma_helper 末段 #2)
  - core/trap.c           (trap_set_exception/interrupt_state 入口 #1)
  - core/interpreter.c    (case OP_WFI 醒后 #3)
  - device/virtio_blk.c   (io_worker drain 完成段 #7)
  - main.c                (lrsc_init / lrsc_destroy lifecycle)

机制:

(1) 数据结构 (lrsc.c file-static, 不嵌 cpu_t — 跟 PLIC plic_ctx_eip / CLINT
    mtimecmp 体例对齐 §7 "shared 数据封装在自己模块内 + cacheline 友好"):

  - per-hart `_Atomic uxlen_t lrsc_reservations[MAX_HARTS]` — 跨 hart 共享的协议状态
    字段; 字粒度 word-aligned PA (`pa & ~3u`); 哨兵 `LRSC_INVALID_ADDR = ~(uxlen_t)0`
    (全 1 永远非法 PA, RV32/RV64 都安全, 不留 RV64 review 债)
  - global `pthread_mutex_t lrsc_buckets[K]` (K = 1 << LRSC_BUCKET_BITS = 64,
    config.h); Fibonacci hash 散列 pa_word: `(uint32_t)pa_word * 2654435761u >>
    (32 - LRSC_BUCKET_BITS)`

  注意: 32-bit 乘法 wrap-around 关键 (不能 cast uint64_t 后再乘 shift — 64-bit
  乘积 shift 26 给 38-bit idx OOB; UBSan 会报). 详 lrsc.c bucket_lock doc.

(2) 七类清除时机 (RV Priv Spec §14.2.1 "Reserved Memory Locations"):

  | # | 触发                            | 入口函数                  | 形态            |
  |---|---------------------------------|---------------------------|-----------------|
  | 1 | context switch / trap           | lrsc_clear_self           | lock-free       |
  | 2 | sfence.vma                      | lrsc_clear_self           | lock-free       |
  | 3 | wfi 醒来                         | lrsc_clear_self           | lock-free       |
  | 4 | fence.i                         | lrsc_clear_self           | lock-free       |
  | 5 | 普通 store 命中 reservation     | lrsc_on_store             | bucket 锁内     |
  | 6 | AMO 命中 reservation            | lrsc_on_store             | bucket 锁内     |
  | 7 | device DMA / virtio_blk 写 RAM  | lrsc_on_device_write      | 锁外 blanket    |

  #1-#4 (lrsc_clear_self): 自己写自己字段 atomic_store INVALID release, 无 race;
    其它路径 atomic_load acquire 读 — 跟"扫所有 hart 清匹配"路径无 happens-before
    依赖 (清 INVALID 单向, 不参与 RV 内存模型 ordering).

  #5-#6 (lrsc_on_store): 拿 bucket(pa) 锁 + 扫 `n_harts` 范围 (§15 第 1 类越界判据,
    cap 数组 / n_harts 扫); reservation == pa_word 则 atomic_store INVALID. 含自己
    (RV spec line 116-118 implementation discretion 选清; Spike/QEMU 同选, 主方案
    "严格不留 spec 漏口" 宗旨一致).

  #7 (lrsc_on_device_write): blanket clear 所有 hart reservation (按 n_harts 扫,
    不查 PA 粒度). 不拿 bucket 锁理由: 单向 atomic_store INVALID (不读不存在 race);
    任何并发 SC 拿 bucket 锁后 atomic_load 看 INVALID 失败, 自然合规.

(3) LR.W / SC.W 函数族 (PA-based, caller 已走 lsu/mmu 路径转换 + perm/MMIO check):

  - `lrsc_lr_w(hart, pa)`: lock-free; memcpy *pa (plain RAM read, 跟 lsu 体例 — 见
    §13 + §15 印证) + atomic_store self.reservation = pa_word; 返 zero-ext value.
  - `lrsc_sc_w(hart, pa, value)`: 拿 bucket lock; 比对 self.reservation:
      不匹配 → atomic_store self.res = INVALID + 释锁 + 返 1
      匹配   → memcpy *pa ← value (plain RAM write) + 扫 n_harts 清匹配 (含自己,
              自然清自己) + 释锁 + 返 0
    无论成败 self.reservation 都被清 INVALID (spec line 59-60 强制).

  *pa access 走 plain memcpy 跟 lsu_load_helper / store_helper 同体例 (不用
  atomic_load/atomic_store_explicit): LR + SC sequence atomicity 由 reservation 协议
  保证 (SC 拿 bucket lock 查 self.reservation), 不由 *pa load/store 那一刀 host-atomic
  保证. amo apply 仍 atomic_fetch_xxx 因 RMW 必须 host-atomic (拆 read+modify+write
  会 lost-update); LR (read-only) + SC (write-only, 锁内) 都不需要这层保证.

  跟 §13 typedef family 印证: PA 字段全部 uxlen_t XLEN-tied (reservation_addr /
  lrsc_on_store signature / amo apply pa 反推); RV64 切换时一起升 uint64_t.

(4) 三层模型 (跟 §8 PMP/MMU/内存三层关系 + 各 isa/* 顶段对偶):

  顶层 inline helper (lrsc.h / amo.h / lsu.h):
    BARE/SV32 分流 + TLB hit fast path; caller 已查 misalign.

  RAM 端副作用入口 (extern, HVA-based; lrsc.c / amo.c / lsu.c):
    lrsc_lr_w / lrsc_sc_w / amo_xxx_apply / store_helper; 三处 caller (顶层 BARE+RAM /
    顶层 SV32 hit / walker RAM) 共用; 末调 lrsc_on_store (store/AMO/SC) 或建/查
    reservation (LR/SC).

  慢路径 walker (mmu.c):
    mmu_walker_helper_load / store / amo_xxx / lr_w / sc_w; TLB miss / 权限不齐
    fall back; walk + atomic OR PTE.A/D + fill TLB + 末调 apply.

  详 access_helper_call_graph.md (7 张 mermaid sequence) + amo.h / lrsc.h 顶段
  3-layer 模型 doc.

  fast/slow path framing 维持 sacred 原则 (a_04 T5 议题已评估; trade_off_log §T.14):
  apply 层不消除 — apply 是 lrsc_on_store + 未来 SMC 锚点 + JIT 块出口 helper 颗粒度
  边界; helper call ~5-10 cycle vs lrsc_on_store ~100-300 cycle, call 占 ~3-5%;
  inline 进 JIT 会失去 host -O3 优化机会 (AsmJit 低级 builder, gcc 看不到 runtime
  emit). 真要降 hot path 攻 lrsc_on_store 内 bucket lock (plan §2 #57).

设计选择 + 理由:

- **per-PA hash 锁 + per-hart atomic 数组** (c 主方案) — b 路径 host CAS 等价 SC 被
  拒, 因 ABA + AA 是 spec rationale 直接禁止的 (zalrsc_manual line 64-77), 不是
  ARM-style implementation latitude. 详 trade_off_log §T.13.

- **reservation 字段放 lrsc 模块 static, 不嵌 cpu_t** — cpu_t 保持 per-hart 私有数据
  集合; 跨 hart 协议状态封装在自己模块内 (§7 monitor model 体例).

- **bucket lock K=64** — 撞桶率 ~5% (Fibonacci hash); 跑 OpenSBI / Linux 实测 lock
  contention 时按 plan §2 #57 升 (spinlock 替 mutex / bucket 数变大 / per-hart
  cacheline 隔离).

- **七类清除时机分流 lock-free vs 锁内 vs 锁外** — #1-#4 自清不需要协议保证, 走
  lock-free 最便宜; #5-#6 真清匹配需保证"同 PA 上 SC vs lrsc_on_store" 串行化, 走
  bucket 锁内; #7 device DMA blanket 不查 PA 不存在 race, 走锁外避免拿无关 bucket.

- **PA 类型 uxlen_t** (跟 §13 印证) — RV64 切换时哨兵 / 字段 / signature 一起升;
  当前 uint32_t 实际值 OK, 但类型不一致就漏 RV64 review trail.

未来改进点:

- aq/rl 精确化 (plan §2 #8) — 当前全 seq_cst, 真做大量 acquire/release sequence
  时按 RV 指令位映射 relaxed/acquire/release/acq_rel.

- bucket lock 性能优化 (plan §2 #57) — spinlock 替 mutex / bucket 数变大降撞 /
  per-hart cacheline 隔离; 真撞 contention 瓶颈时升.

- ARM64 host 兼容 (plan §2 #50) — *pa plain memcpy 跟 lsu 同源 latent race
  (cross-hart RAM access 不走同步原语); TSan 02_lr_sc_spinlock 已报 (项目接受, stub.S
  顶段说明). ARM64 host 切换时跟 lsu 一起升 atomic.

- LR/SC 跨 reservation set 的非法操作检测 — RV spec 禁止 LR/SC 之间出现 load/store/
  其他原子/跨页跳转/超过 16 指令. 当前不主动检查 (出现时 reservation 自然被清,
  SC 自然失败, 语义自洽); 真要 audit guest 行为时加.
